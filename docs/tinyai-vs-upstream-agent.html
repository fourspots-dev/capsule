ARCHITECTURE COMPARISON

同源目标，不同阶段

上游已经是一个功能完整、测试充分的真实浏览器 Agent；tinyai Agent 2.0 则是一份面向可恢复运行时和未来代码沙盒的内核设计。前者胜在已落地和功能广度，后者胜在边界清晰、权限粒度与恢复模型。

对比对象 目标设计 vs 上游实现 上游版本 0.15.1 上游规模 67,613 行源码 基准日期 2026-10-30
一句话结论

如果现在要比“谁更完整”，上游明显领先；如果比“谁更适合继续扩展成 Web + 受限沙盒 Coding Agent”，目标设计的架构方向更合理，但关键能力仍停留在设计阶段。

上游领先

已实现功能

浏览器工具、附件、压缩、子 Agent、模型路由和真机回归已落地。

设计领先

内核边界

显式状态机、事件日志、写入租约和能力级审批更便于长期演进。

设计领先

沙盒方向

目标设计预留 ExecutionProvider、WorkspaceProvider 和受限沙盒边界。

双方不足

真正 Coding

两边都还没有生产级的代码工作区、PTY、文件系统和测试执行闭环。

02

产品定位差异

上游是“在用户真实浏览器里完成网页任务”的成品型 Agent；目标设计更像“可承载多种执行环境的 Agent 操作系统内核”。

上游

真实浏览器操作员

按标签组组织任务，直接复用用户登录态，强调网页观察、点击、输入、文件上传、下载、录制和技能复用。

目标设计

Agent Kernel

把任务状态、上下文、工具、权限和执行环境抽象为独立模块，浏览器只是第一个 Provider，后续可接容器或 WASM。

尚未覆盖

完整 Coding Agent

需要工作区、代码编辑、测试、PTY、网络隔离、artifact、diff 审阅和合并协议，双方都还没有形成完整闭环。

胜出用户能力与产品完整度上游已有真实 UI、丰富工具和浏览器边界细节。
胜出长期架构可演进性目标设计把运行、执行和权限解耦得更彻底。
共同缺口受限代码执行环境需要全新沙盒、工作区和验证产品面。

关键判断

上游架构强项

  • 事件、时间线、持久化和 UI 已有闭环。
  • 工具批次调度、路径冲突调度、取消和审批均已实现。
  • 上下文溢出、媒体降级、模型恢复已有真实代码路径。
  • 大量迁移自真实产品的边界行为，细节更可靠。

目标设计强项

  • 状态机、快照、事件和写入租约是显式内核契约。
  • 能力级权限可覆盖文件、进程、网络，而不只浏览器动作。
  • ModelGateway、ToolExecutor、ExecutionProvider 边界更清晰。
  • 未来沙盒不必修改 Agent 主循环。

05

运行与恢复

上游的运行机制已经比“聊天 + Promise”成熟很多，但目标设计把可恢复性提升为系统级不变量。

UPSTREAM · IMPLEMENTED

后台会话循环

每个会话有内存 loop、队列、时间线、AbortController、挂起审批与端口订阅。会话可以通过回放记录和 IndexedDB 恢复。

  • 回合期间拒绝新的普通回合，支持消息排队。
  • 工具批次支持并发调度和路径冲突控制。
  • 停止使用 AbortController，并传播到工具、模型和子 Agent。
  • 上下文溢出后可以自动压缩并继续。
TARGET · DESIGNED

持久任务状态机

任务从创建开始就有明确状态、revision、事件日志和写入租约。模型、工具、审批和人工等待都是状态的一部分。

  • 快照用于快速恢复，事件用于审计和 UI 重放。
  • 同一任务只有一个写入者，降低多上下文竞争。
  • 副作用有幂等键，恢复前必须确认动作结果。
  • 取消状态可跨进程持续，而不是只存在内存中。
关键差异上游已有运行闭环，但会话 loop 仍带大量内存状态；目标设计更重视跨进程一致性，不过代码尚未验证这些不变量。
目标设计要学习上游的队列、端口订阅、挂起审批对账、标签页恢复、回放时间线和真机 smoke 都是目标设计必须补齐的实现细节。
上游需要目标设计如果把 Agent 从浏览器产品扩展成代码 Agent，单进程 session loop 和浏览器域权限不足以覆盖工作区租约、进程和文件副作用。
06

上下文压缩与溢出恢复

这是上游明显领先、最值得优先移植的模块。

上游已实现

CompactionManager

  • 估算文本、工具 schema 和媒体 token。
  • 保留近期用户消息，生成第一人称 handoff 摘要。
  • 工具结果规范化、缺失结果合成、重复调用去重。
  • 媒体块转换为标签、降级请求、移除媒体后重试。
  • 上下文溢出时压缩后重试，并提供失败分类。
  • UI 有上下文余量、压缩进度、摘要查看与取消。
目标设计

预算化 ContextManager

  • 规则、计划、对话、观察和输出预留分区。
  • 70%/85%/95% 分级处理。
  • 大结果进入 ArtifactStore，只回传摘要和引用。
  • 页面、文件、工具结果带来源与信任标签。
  • 结构化 checkpoint 保留计划、证据、决策和未解决问题。
结论

目标设计的上下文分区和 artifact 思路更通用，但当前没有实现。近期不应重新发明压缩算法，应先以“上游 CompactionManager 为行为基线”实现目标内核的 ContextManager，再增加来源标签和 artifact 引用。

08

权限与审批

上游优化真实浏览器产品的用户摩擦；目标设计优化跨文件、进程和沙盒的可扩展安全边界。

上游实现

域 + 浏览器动作

权限按域名保存，动作限定为 navigate、interact、read_page、execute_js。产品提供逐次审批和完全授权两种模式。

  • 适合浏览器场景，用户可以直接“在这个站点始终允许”。
  • 只读工具通常自动放行，交互和 JS 执行可被拦截。
  • 页面目标、元素选择器和动作影响已有较细 UI 描述。
  • 完全授权模式仍然扩大了整体信任边界。
目标设计

能力 + 动作摘要

策略关注 browser.action、fs.write、process.exec、network.connect 等能力，审批绑定具体动作摘要、任务 revision 和 TTL。

  • 能统一覆盖浏览器、文件、命令和子 Agent。
  • 参数变化后旧审批失效，降低重放风险。
  • 更适合未来沙盒和生产代码操作。
  • 交互复杂，必须通过 Eval 和可用性测试校准。
不能简单判断谁更安全

上游已经有经过测试的站点授权和挂起审批恢复；目标设计纸面上更精细，但还没证明不会产生审批疲劳或策略绕过。最合理方式是保留上游的站点授权 UX，同时引入目标设计的能力级后端策略。

09

工具与模型协议

上游在协议容错和工具执行细节上领先不少，目标设计主要加强工具契约和 Provider 抽象。

上游已实现

协议与工具执行

  • 非法 JSON 和 schema 不通过会生成明确错误结果，而不是执行空参数。
  • 一次模型响应中的多个工具调用可按批次调度。
  • PathAccessScheduler 处理工具之间的路径冲突。
  • 工具停止、用户中断、超时和最终结果拥有不同语义。
  • OpenAI、Anthropic、AgentGW 和 BYOK 端点统一到 ChatProvider。
  • 支持 429、网络重试、模型切换、媒体降级和严格重发。
目标设计

结构化、跨环境契约

  • 每个工具声明 capability、effect、risk、timeout、cancel、idempotent。
  • 输入和输出都带 schema，输出可引用 artifact。
  • ModelGateway 统一模型事件、usage、错误和重试策略。
  • ExecutionProvider 可承载浏览器、容器、WASM 和进程。
  • 工具实现不直接依赖具体浏览器 API。
协议点上游目标设计
参数校验已实现 JSON + schema 校验设计为强制契约
工具并发已有批次调度与路径冲突锁设计为执行器能力，未实现
取消AbortSignal 贯穿模型、工具和子 Agent每个工具声明 cancellable，目标更严格
幂等部分工具自身描述幂等，缺少统一副作用账本统一 idempotency key + ledger
模型恢复已实现重试、降级和模型切换设计为 ModelGateway 策略
结果类型文本、图像、结构化工具结果结构化结果 + artifact 引用
10

沙盒与 Coding Agent

这是双方真正的共同空白，也是两套设计区别最大的未来方向。

上游

真实浏览器为主

浏览器标签组、CDP、页面工具和 AgentGW 已经完整。仓库里没有面向代码工作区、PTY、测试和受限文件写入的产品级闭环。

目标设计

已定义执行边界

定义 WorkspaceProvider、SandboxProvider、ArtifactStore、SecretBroker 和独立 ExecutionProvider，但还没有实现。

仍需补齐

真正的 Coding UX

文件树、diff 审阅、终端、测试失败、任务检查点、补丁合并、资源配额和回滚。

面向受限沙盒的必要差异

执行位置上游主要执行浏览器工具；Coding Agent 需要独立进程或 microVM，不能让扩展直接获得宿主文件系统权限。
权限模型域名授权无法覆盖 fs.write、process.exec 和 network.connect，因此目标设计的能力级策略更合适。
并发写上游子 Agent 可操作浏览器标签组；未来多个 Coding Agent 必须使用独立 worktree 或 sandbox。
验证闭环网页 Agent 更看重观察和操作成功；Coding Agent 必须以测试、build、lint、diff 和独立审查作为完成标准。
网络隔离浏览器 Agent 依赖现实网络和登录态；沙盒默认应禁网，只开放明确的依赖与 API allowlist。
11

工程成熟度

上游最大的护城河不是某个功能，而是大量边界行为和回归验证。

实测

67,613 行

lib + entrypoints 的 JS/TS/CSS 源码规模。

实测

171 个测试文件

覆盖 Provider、工具、存储、时间线、子 Agent 和 UI。

实测

1,353 个测试入口

由 tests/*.mjs 中的 test(...) 统计，不等同于断言总数。

流程

真机 Smoke

加载扩展到一个真实 Chrome，验证选项页、BYOK、附件和多宽度布局。

上游工程优势

  • WXT 管理入口、构建、打包和 manifest。
  • 单测直接 import 真实模块，大量协作方通过接口注入。
  • 真机套件覆盖扩展加载、Service Worker 重启、BYOK 路由和布局。
  • 版本号、产物清单、CSS 类名和协议均有闸门。
  • 迁移自真实产品的异常、竞态和兼容行为无法靠短时间重写补齐。

但工程成本也很高

  • 多个模块达到 1,800–3,800 行，阅读和修改成本高。
  • 迁移注释和兼容层占比较大，目标和新架构并不完全一致。
  • 浏览器域权限与同进程子 Agent 难以直接扩展到代码沙盒。
  • 高测试量值得借鉴，但不应把现有大模块原样搬进新内核。
12

复用策略

最有效的路线不是二选一，而是“目标设计定边界，上游实现做行为基线”。

可立即作为行为基线和测试资产

  • 上下文 token 估算、溢出恢复、媒体降级和压缩摘要规则
  • 非法工具参数、缺失工具、重复工具结果和孤儿工具结果处理
  • 工具批次调度、路径冲突控制、Abort 传播和超时语义
  • 子 Agent 实时事件、父子取消和卡片状态机
  • 模型发现、429 重试、模型不可用切换和 provider 错误分类
  • IndexedDB 记录结构、回放、挂起审批对账和真机 smoke fixture

需要抽象后接入目标内核

  • 把会话时间线映射成 TaskSnapshot + AgentEvent
  • 把浏览器工具包装成 ExecutionProvider
  • 把产品级审批模式映射到 PolicyEngine profile
  • 把同进程子 Agent 改为 SubagentCoordinator 管理的子任务
  • 把聊天回放升级为可审计事件重放和写入租约
  • 把 UI 组件保留为事件投影，不直接调用工具

不建议直接复制

  • 把 1,800–3,800 行迁移模块整体搬入新内核。
  • 让所有子 Agent 与父 Agent 共享同一进程和写权限。
  • 延续“浏览器域名 + 四个动作”作为唯一权限模型。
  • 用一次完全授权覆盖未来文件、命令和网络执行。
  • 用聊天消息数组代替任务状态、审批和副作用记录。
  • 在未测量前引入无限层级 Agent 或复杂多 Agent 编排。
13

收敛路线

先对齐上游最成熟的行为，再验证目标设计新增的运行时和权限约束，最后接沙盒。

A0

建立上游行为语料

不做重构，先从上游测试和真机套件提取可重复场景。

  • 压缩前后 token 与保留消息 fixture
  • 非法工具、工具并发、取消和父任务中断 fixture
  • 子 Agent 事件序列与最终结果 fixture
  • Provider 重试、模型恢复和媒体降级 fixture
A1

对齐任务与上下文

让目标内核先达到上游已经证明的工作能力。

  • 持久任务、事件回放和写入租约
  • 上下文自动压缩与 overflow recovery
  • 工具 schema 校验、批处理和真实取消
  • Provider 重试、模型切换和错误分类
A2

对齐子 Agent

先移植研究员与审查员的只读子任务。

  • 父上下文 brief 与独立 child context
  • 实时子时间线、预算和递归取消
  • 父权限与角色白名单求交集
  • 结构化结果与证据校验
A3

安全差异化

引入目标设计真正优于浏览器产品的部分。

  • 能力级 PolicyEngine 与 action approval
  • 来源标签与提示注入隔离
  • ArtifactStore、SecretBroker 和审计 trace
  • 确定性 Eval + 真实 Chrome A/B
A4

Coding 沙盒

只有完成 A1–A3 后再接代码执行。

  • Workspace、PTY、文件、patch 和测试
  • 只写工作区、网络 allowlist、资源限制
  • 独立 worktree 与写型子 Agent
  • diff、测试报告、回滚和合并
