IMPLEMENTATION DESIGN · REVIEW v0.1

在成熟行为上，重建一个可演进的 Agent 内核

本文把上游已经验证的浏览器 Agent 行为，与 tinyai 的持久任务、能力权限、上下文档位和沙盒边界合并成一份可实现、可验收的分模块设计。评审意见可直接标注在页面中，作为下一轮开发的输入。

01

实现基线与设计取舍

本设计不重写上游的成熟行为，而是把这些行为映射到更稳定的任务与执行边界中。

本设计相对上游的关键调整

新增

持久任务状态机

从“会话正在运行”提升到明确 TaskStatus、revision、检查点和写入租约。

新增

能力级策略

浏览器域授权保留为用户 UX，后端扩展到文件、进程、网络和子任务能力。

新增

执行适配层

浏览器与未来沙盒共用 ToolExecutor 和 ModelGateway，不污染 Agent 主循环。

实现顺序约束

先完成 B1–B3 的稳定行为，再引入子 Agent 和沙盒。Coding 能力不能先于任务恢复、权限和上下文预算实现。

05

ControlPlane / UI Projection

UI 只发布命令和消费事件，不直接修改任务或调用执行器。

M0

ControlPlane / UI Projection

侧栏、审批、计划、产物与文档评审状态

P0 · Interface
B1 session portstimeline reducerB8 smoke UI

设计要点

  • CommandBus 接收 Start/Pause/Resume/Cancel/Approval 等意图。
  • EventProjection 从 TaskSnapshot 和增量事件重建 timeline、计划与审批。
  • 流式文本只更新临时投影，最终内容以持久事件为准。
  • UI 断开或重连时发送 snapshot，再补发 lastEventSeq 之后的事件。
  • 审批卡展示动作、目标、风险和过期时间，不能只显示工具名。
  • 设计文档的修订批注与 Agent 运行事件分开存储，避免产品状态污染。

核心契约

interface UICommandBus {
  send(command:
    | StartTaskCommand
    | PauseTaskCommand
    | ResumeTaskCommand
    | CancelTaskCommand
    | ApprovalDecision
  ): Promise<CommandAck>;
}

interface EventSubscription {
  taskId: string;
  afterSeq: number;
  onSnapshot(snapshot: TaskSnapshot): void;
  onEvent(event: AgentEvent): void;
  onReconnect(): void;
}

交互

页面加载先拉取 TaskSnapshot，再按 lastEventSeq 订阅事件；用户操作只通过 CommandBus 进入 Runtime。Runtime 产生 plan/tool/approval/notice 事件，Projection 更新视图，不反向写任务状态。

借鉴与增强

沿用上游端口广播、时间线 reducer、审批卡和工具卡交互；新增 revision/seq 断线重连协议，避免 UI 与服务化 Runtime 连接中断后丢失事件。

验收

  • 断开再连接不会重复或遗漏时间线事件。
  • UI 刷新后审批、计划和运行状态一致。
  • 修订批注和 Agent 事件不互相覆盖。
  • 390px 与桌面宽度无关键内容遮挡。
06

TaskRuntime

系统的唯一任务状态推进者。负责调度，不负责模型协议、工具实现或 UI 展示。

M1

TaskRuntime

任务生命周期、预算、并发和恢复

P0 · Core
B1 session-loopAbortSignal消息队列

设计要点

  • 采用显式状态机，任何迁移都先 append event，再更新 snapshot。
  • 单任务同一时刻只有一个写入租约；不支持两个执行者同时推进。
  • 预算按步骤、token、费用和 wall time 分别限制。
  • 取消是持久状态，必须传播给模型、工具、审批和子任务。
  • 恢复时根据 last stable event 决定重试、吸收结果或等待人工确认。

不负责

工具业务逻辑、浏览器 API、消息渲染和模型协议解析。

核心契约

interface TaskRuntime {
  start(command: StartTask): Promise<TaskId>;
  run(taskId: string): Promise<void>;
  pause(taskId: string, reason: string): Promise<void>;
  resume(taskId: string): Promise<void>;
  cancel(taskId: string): Promise<void>;
  resolveApproval(decision: ApprovalDecision): Promise<void>;
  recover(taskId: string): Promise<RecoveryDecision>;
}

交互

接收 UI 的 Start/Pause/Resume/Cancel，调用 StepEngine 推进一次模型或工具步骤；每一步通过 TaskRepository 持久化，通过 EventBus 向 UI 投影。收到 ApprovalService 决议后从 waiting_approval 恢复。

借鉴与增强

保留上游的单会话队列、running 锁和 AbortController 语义；新增 lease、revision、显式 waiting 状态和恢复决策，避免只依赖内存 loop。

验收

  • 关闭 UI、刷新扩展和 worker 重启后任务可恢复。
  • 取消后不再产生新模型请求或工具副作用。
  • 同一任务并发执行请求被租约拒绝。
  • 预算耗尽进入 paused，不会静默失败。

07

TaskRepository / EventLog

事实数据与 UI 时间线分离。事件是不可变审计记录，快照是可快速恢复的物化视图。

M2

TaskRepository / EventLog

持久任务、事件、回放和 artifact 索引

P0 · Core
B1 timeline reducerB7 IndexedDBreplay

设计要点

  • 任务内事件严格单调 seq；事件 ID 全局唯一。
  • 快照保存 revision 和 lastEventSeq，写入时做 CAS。
  • 租约包含 ownerId、expiresAt 和 fencing token。
  • 长结果、截图和日志进入 ArtifactStore，事件只保存摘要与引用。
  • 事件 schema 版本化，升级提供 replay migration。

核心契约

interface TaskRepository {
  create(task: TaskRecord): Promise<void>;
  load(taskId: string): Promise<TaskBundle | null>;
  append(event: AgentEvent, lease: FencingLease): Promise<void>;
  saveSnapshot(snapshot: TaskSnapshot, expectedRevision: number): Promise<void>;
  replay(taskId: string, throughSeq?: number): AsyncIterable<AgentEvent>;
  acquireLease(taskId: string, ownerId: string): Promise<FencingLease>;
}

交互

Runtime 每次状态迁移调用 append；成功后再 saveSnapshot。UI 从 snapshot 加增量事件重建；Eval 可以重放到任意事件位置。ArtifactStore 提供受控的正文和二进制读取。

借鉴与增强

借鉴上游 chat records/blobs/chats、时间线 reducer 和 replay 修复逻辑。新增 fencing lease、CAS revision 与副作用账本，解决多个执行上下文同时写入的问题。

验收

  • 重复 append 同一 eventId 不产生重复状态。
  • 旧 lease 的写请求被拒绝。
  • 从任意合法快照重放事件得到相同投影。
  • 存储升级后旧会话可迁移或明确标记不可迁移。
08

ModelGateway

统一供应商差异，向下暴露稳定的模型事件，不让主循环直接理解 Chat Completions 或 Messages 协议。

M3

ModelGateway

流式协议、重试、模型恢复和 usage

P0 · Port + adapt
B6 providers.jsretrymodel recoverymedia degrade

设计要点

  • 统一 ModelEvent：text delta、reasoning、tool call delta、usage、finish、error。
  • 只处理一次模型请求，不执行工具；工具调用结果回传给 StepEngine。
  • 429/网络错误指数退避，保留 provider request ID 和 Retry-After。
  • 上下文溢出、媒体过大、协议结构错误走可观测降级路径。
  • 模型不可用时允许切换连接，但必须记录 from/to 与原因。
  • 所有密钥只通过连接解析器注入，不进入事件和日志。

核心契约

interface ModelGateway {
  stream(request: ModelRequest, signal: AbortSignal): AsyncIterable<ModelEvent>;
  discoverModels(connection: Connection): Promise<ModelDescriptor[]>;
  classifyError(error: unknown): StructuredError;
  withBudget(request: ModelRequest, budget: OutputBudget): ModelRequest;
}

交互

StepEngine 构建消息和工具 schema，ModelGateway 输出规范化事件。ContextManager 接收 overflow 结果并压缩；TaskRuntime 接收模型切换通知并更新配置快照。

借鉴与增强

直接借用上游的 provider 转换、错误分类、媒体降级、重试和模型切换行为。目标设计增加统一 usage/cost 事件与可配置重试策略，便于后续沙盒 Agent 共用。

验收

  • OpenAI 兼容和 Anthropic fixture 产生相同内部事件序列。
  • 429、连接中断、超时和内容过滤有不同错误代码。
  • 模型切换后 usage 连续累计。
  • API key 不出现在 trace、tool result 或 UI 文本中。
09

ContextManager

优先复用上游经过真机验证的压缩行为，再扩展 artifact 引用与来源标签。

M4

ContextManager

预算、压缩、溢出恢复和大结果 artifact

P0 · Port first
B3 compaction.jstoken estimateoverflow recoverymedia degrade

设计要点

  • 输入按 system、task、plan、conversation、observation、reserve 分区。
  • 达到预警阈值先减少可重建观察，再触发结构化 compaction。
  • 保留最近用户消息和明确 pinned facts；摘要记录覆盖 event seq。
  • 工具大输出进入 artifact，模型只接收摘要、长度和读取引用。
  • 图片/音频过多时先降级为标签，再移除媒体后重试。
  • 压缩失败不破坏原历史；任务进入 paused 或 error。

核心契约

interface ContextManager {
  build(task: TaskSnapshot, events: AgentEvent[]): ModelContext;
  estimate(context: ModelContext): TokenEstimate;
  compact(input: CompactInput, signal: AbortSignal): Promise<ContextCheckpoint>;
  handleOverflow(error: ContextOverflow, signal: AbortSignal): Promise<ModelContext>;
  artifactize(result: ToolResult): Promise<ArtifactRef>;
}

交互

StepEngine 在模型请求前调用 build；ModelGateway 返回 overflow 时调用 handleOverflow；成功后 append context.compacted 事件并保存 checkpoint。ToolExecutor 对大结果调用 artifactize。

借鉴与增强

B3 是本设计最重要的行为来源：token 估算、保留消息、handoff 摘要、媒体降级、结构化 normalization 都应先跑 fixture 对齐。新设计额外加入来源标签和 artifact 引用，但不能牺牲上游已验证的压缩顺序。

验收

  • 压缩前后 token 下降且关键用户消息保留。
  • 媒体降级不改变任务最终语义。
  • 大工具输出只以引用进入后续上下文。
  • 压缩取消后恢复原 checkpoint，不产生半写状态。
10

ToolExecutor

所有副作用都从这个入口通过。工具执行器本身不判断任务是否完成，也不更新 Agent 业务状态。

M5

ToolExecutor

参数校验、策略授权、并发、执行和取消

P0 · Port + unify
B2 tool batchschema validationPathAccessSchedulerAbortSignal

设计要点

  • 收到 tool call 后先 JSON parse 和 schema 校验，失败绝不按空参数执行。
  • 每个工具声明 capabilities、effects、risk、timeout、cancel 和 idempotent。
  • 只读工具可以并发；读写冲突由资源锁或 PathAccessScheduler 串行。
  • 执行前写入 tool.started 和 idempotency key，执行后写 tool.completed/failed。
  • 真实的取消要传递到 Provider 和底层 API，不能只做 Promise race。
  • 大结果交 ArtifactStore，返回 ToolResult 引用而不是无限文本。

核心契约

interface ToolDefinition<I, O> {
  name: string;
  capabilities: Capability[];
  effects: Effect[];
  risk: Risk;
  idempotent: boolean;
  inputSchema: Schema<I>;
  outputSchema: Schema<O>;
  execute(input: I, ctx: ToolContext): Promise<O>;
  cancel?(callId: string): Promise<void>;
}

interface ToolExecutor {
  prepare(calls: ToolCall[]): PreparedCall[];
  executeBatch(calls: ToolCall[], signal: AbortSignal): Promise<ToolResult[]>;
  cancel(taskId: string, callId: string): Promise<void>;
}

交互

StepEngine 把同一模型响应中的 calls 交给 ToolExecutor。ToolExecutor 调用 PolicyEngine 获得 allow/deny/approval，再调用 ExecutionProvider。结果和错误进入 EventLog 并回填模型消息。

借鉴与增强

上游已经实现参数校验、批次调度、路径冲突、用户中断和结果截断。首版直接复用这些行为；新增统一 idempotency ledger 和 ToolDefinition 的跨环境 effects 声明。

验收

  • 非法 JSON 被拒绝且模型能收到结构化修复提示。
  • 只读并发不破坏结果顺序。
  • 同一文件或资源的冲突写操作不会并发执行。
  • 取消发生后底层工具在可测时间内停止。
  • 重复调用不会重复产生已知副作用。

PolicyEngine / ApprovalService

保留上游按站点授权的易用性，同时把后端决策抽象成跨浏览器、文件、网络和进程的能力策略。

M6

PolicyEngine / ApprovalService

能力策略、风险决定和可恢复审批

P0 · Security critical
B5 domain permissionspending approval registrypermission restore

设计要点

  • PolicyEngine 返回 allow / ask / deny，不直接弹 UI。
  • 审批绑定 taskId、revision、action digest、目标资源和 TTL。
  • 站点授权保留为便捷 profile，但不能覆盖能力硬拒绝。
  • 高风险默认逐次确认；full access 只能作为显式受限 profile。
  • 所有审批、消费、过期和拒绝都写入事件日志。
  • 子 Agent 权限与父权限求交集，永远不能提升。

核心契约

interface PolicyEngine {
  decide(action: NormalizedAction, task: TaskSnapshot): PolicyDecision;
  createApproval(action: NormalizedAction, task: TaskSnapshot): ApprovalRequest;
  validateApproval(input: ApprovalDecision): ApprovalValidation;
  consumeApproval(id: string, actionDigest: string): Promise<void>;
}

type PolicyDecision =
  | { type: "allow"; reason: string }
  | { type: "ask"; approval: ApprovalRequest }
  | { type: "deny"; reason: StructuredError };

交互

ToolExecutor 在副作用前调用 decide。ask 时 TaskRuntime 进入 waiting_approval；UI 显示审批卡；ApprovalService 验证 revision 和 digest 后，Runtime 回到 waiting_tool。重启后从未过期审批继续等待。

借鉴与增强

上游的域名 + 四类动作授权、挂起审批对账和请求取消都可以保留。扩展点是把 domain action 映射到 capability，并增加 action digest、TTL 和子任务权限求交集。

验收

  • 修改工具参数后旧审批失效。
  • 审批等待跨扩展重启仍可见且可继续。
  • 子任务无法调用父任务未授予的工具。
  • 站点永久授权不能绕过硬拒绝能力。

BrowserProvider

标签组、CDP、frame、页面工具和下载

P0 · Reuse behavior
B1 tab-groupB2 page toolsframe-readCDP guard

设计要点

  • 一个 Task 绑定一个标签组，子 Agent 默认创建自己的工作标签。
  • 封装 attach、Page.enable、dialog guard 和命令超时。
  • 提供 snapshot、find、read_page、click、fill、upload、download 等能力。

  • frame、PDF、图片等不可读页面返回明确错误而不是空成功。

interface BrowserProvider extends ExecutionProvider {
  ensureTaskGroup(taskId: string): Promise<TabGroupId>;

交互

借鉴与增强

上游的标签组隔离、CDP attach 重试、dialog guard、frame 读取、快照 ref 和真实鼠标事件都应保留。新设计只需增加统一 action 模型、artifact 引用和与沙盒 Provider 相同的健康检查。

验收

  • 不同任务标签组互不串页。
  • 页面有 JS dialog 时非 dialog 命令被明确阻止。
  • frame/PDF/图片失败有可恢复错误。
  • 任务恢复后能重新绑定仍存活的标签组。

上游已经证明子 Agent 的价值；本设计把它的执行、权限、预算和结果契约化。

SubagentCoordinator

子任务树、独立上下文、权限与结果汇总

P1 · Port + govern
B4 runSubagentTaskchild eventsparent abortsubtask UI

设计要点

  • 第一版只开放 Researcher 和 Reviewer，均为只读角色。
  • 子任务从零上下文开始，只接收 brief、facts、artifact refs 和白名单工具。
  • 父权限与角色白名单求交集；子任务不能申请提升权限。
  • 子任务有独立步骤、token、时间、费用预算。
  • 子事件实时投影到父时间线，但最终只回传结构化 ChildResult。
  • 父取消递归取消后代；孤儿任务在启动时清扫。
  • 写型 Implementer 在 P2 沙盒和 worktree 就绪后再开放。

核心契约

interface SubagentCoordinator {
  spawn(parent: TaskSnapshot, spec: ChildTaskSpec): Promise<TaskId>;
  send(childTaskId: string, message: string): Promise<void>;
  wait(childTaskId: string, signal: AbortSignal): Promise<ChildResult>;
  cancelTree(taskId: string, reason: string): Promise<void>;

}

交互

借鉴与增强

上游的单类型子 Agent、零上下文 brief、子标签页、实时事件和父 AbortSignal 传播是直接基线。新增角色、权限交集、预算和结构化结果，避免子 Agent 成为隐形的无限成本来源。

验收

  • 子 Agent 启动时看不到父完整 transcript。
  • 子 Agent 无法调用父未授权工具。
  • 父取消后所有后代停止并产生 cancelled 事件。
  • 子结果超过 schema 或缺少证据时不自动并入任务完成。

Planner / Verifier

保持轻量。计划用于减少迷航，验证用于阻止“模型说完成”。

M9

Planner / Verifier

短计划、进度检测、完成条件和独立验证

P1 · New
B1 todo compressionupstream stopReason新增 verifier

Planner 要点

  • 计划项只保存短标题、状态和验收信号，不保存长链思考。
  • 工具结果更新最近观察、未解决问题和计划状态。
  • 连续重复调用、重复失败或预算增长过快触发 replan。
  • 用户修改目标时追加目标变更事件，不覆盖旧目标。

Verifier 要点

  • 模型声称完成不等于 completed；必须有确定性检查。
  • 浏览器任务用观察结果验证；Coding 任务用测试、build、diff 验证。
  • Verifier 失败返回结构化原因，指导下一轮修正。

核心契约

interface PlanState {
  goal: string;
  constraints: string[];
  items: Array<{
    id: string;
    title: string;
    status: "pending" | "running" | "done" | "failed";
    acceptance?: string;
  }>;
  openQuestions: string[];
  lastProgressAt: number;
}

interface Verifier {
  verify(snapshot: TaskSnapshot, evidence: ArtifactRef[]): Promise<VerificationResult>;
}

交互

StepEngine 在每次工具结果后更新 Planner；模型返回无工具最终文本时调用 Verifier。Verifier 通过则 TaskRuntime 进入 completed；失败则把结构化原因写回上下文并重新进入 running。

借鉴与增强

上游已有 todo 列表压缩、stop reason 和失败分类，可复用其状态表述。新设计增加显式验收信号和 Verifier，避免浏览器 Agent 的“文本完成”直接升级为 Coding Agent 的“代码完成”。

验收

  • 相同无效工具连续调用达到阈值时触发重规划。
  • 无证据的完成声明不会进入 completed。
  • 计划更新不会丢失用户原始目标。
  • Coding task 测试失败时不会生成成功结果。

TraceRecorder / EvalHarness

结构化 trace、脱敏、回放和场景评测

P0/P1 · Port discipline
B8 unit testsreal Chrome smokediagnosticsinventory gates

设计要点

  • 每个 model/tool/approval/child 调用都是带父子关系的 span。
  • 记录延迟、token、费用、重试次数、错误代码和 artifact 引用。
  • 记录前执行字段级脱敏；full body 只进入受控 artifact。
  • Eval 使用脚本化模型、假 Provider、真实工具 fixture 和少量联网测试。
  • 以任务结果和副作用状态判定成功，不比较完整模型文本。
  • 真机 smoke 验证扩展安装、Service Worker 重启、BYOK 和布局。

核心契约

interface TraceRecorder {
  startSpan(input: StartSpan): TraceSpan;

借鉴与增强

沿用上游的“真 import 测试、可注入协作方、真机 smoke、产物 inventory”。新设计把 trace 和 Eval 作为内核一等模块，并明确比较副作用而非只比较输出文本。

验收

  • 失败场景可从 trace 定位到具体 step 和 tool call。
  • 金丝雀 secret 不出现在 console、事件和导出中。
  • 核心 Eval 无网络也能稳定运行。
  • 真机 smoke 覆盖 SW 重启和审批恢复。

Workspace / SandboxProvider

先定义接口，后实现沙盒。代码执行不能通过网页 evaluate 偷渡。

M11

Workspace / SandboxProvider

受限文件、PTY、测试、网络和 artifact

P2 · Future integration
upstream browser boundarynew sandbox boundaryartifact contract

设计要点

  • 工作区是唯一可写目录，根文件系统和宿主目录只读或不可见。
  • 提供 read/write/patch/search/git/test/run/artifact 等原子能力，不把任意 shell 字符串作为唯一接口。
  • PTY 和长进程需要有 session、输出流、超时和取消。
  • 网络默认关闭，按域名或代理 allowlist 开通。
  • 密钥由 SecretBroker 注入短时环境变量，不进入命令文本和日志。
  • 写型子 Agent 使用独立 worktree 或 sandbox，父 Agent 负责 diff 和合并。

核心契约

interface SandboxProvider extends ExecutionProvider {
  createWorkspace(taskId: string, template: WorkspaceTemplate): Promise<WorkspaceRef>;
  readFile(path: string): Promise<FileChunk>;
  applyContextPatch(patch: ContextPatch): Promise<PatchResult>;
  applyUnifiedDiff(patch: UnifiedPatch): Promise<PatchResult>;
  search(query: SearchQuery): Promise<SearchResult[]>;
  startProcess(spec: ProcessSpec): Promise<ProcessHandle>;
  runTests(spec: TestSpec, signal: AbortSignal): Promise<TestReport>;
  snapshot(workspace: WorkspaceRef): Promise<SnapshotRef>;
  restore(snapshot: SnapshotRef): Promise<void>;
}

交互

ToolExecutor 将 fs/process/test 调用路由到 SandboxProvider；模型默认通过 ContextPatch DSL 编辑，工具内部生成 unified diff；外部补丁走独立 applyUnifiedDiff 入口。PolicyEngine 检查工作区根、网络和命令能力；Verifier 读取 TestReport；ArtifactStore 接收 diff、日志和截图。TaskRuntime 不感知容器实现。

借鉴与增强

上游 BrowserProvider 已经把执行、标签、取消和结果封装得很好；沙盒遵循同样模式，但使用独立进程和资源限制。不要把宿主权限交给浏览器扩展，也不要复用网页浏览器 Profile 作为代码执行环境。

验收

  • 路径穿越和 symlink 逃逸被拒绝。
  • 任务只能写自己的工作区。
  • CPU、内存、PID、磁盘和执行时间有硬限制。
  • 网络默认关闭，allowlist 之外请求失败。
  • 测试失败和进程超时返回结构化结果。
  • 快照恢复后工作区内容可重放。

总体验收与评审清单

以下项目是开发进入下一阶段的门槛，不是功能愿望清单。

运行时

  • 任务可暂停、恢复、取消并跨重启保持状态
  • 状态迁移都写入事件日志和 revision 快照
  • 所有工具副作用有幂等键和审计记录
  • 模型、工具和审批都能被真实取消
  • 旧执行者的写入被 fencing lease 拒绝

Agent 能力

  • 压缩、overflow 恢复和媒体降级通过上游 fixture
  • 子 Agent 使用独立上下文、权限和预算
  • 工具批次遵守并发和冲突规则
  • 完成状态必须经过 Verifier
  • UI 重放得到一致的 timeline 和审批状态

安全

  • 站点授权不能绕过能力硬拒绝
  • 子 Agent 无法提升父权限
  • Secret、Cookie 和 API key 不进入普通 trace
  • 网页和仓库内容始终标记为 untrusted
  • 沙盒路径、网络和进程限制有逃逸测试

工程

  • 核心模块可用假模型和假 Provider 单测
  • 真机 smoke 覆盖加载、重启、BYOK 和布局
  • 构建、产物清单和版本闸门进入 CI
  • Eval 报告包含副作用、成本和恢复指标
  • 所有评审批注导出为可追溯修订 JSON
开发前必须确认的设计决策
  • TaskRuntime 首版放在扩展 offscreen document、后台服务，还是服务化运行？
  • 首版是否保留上游“完全授权”模式，还是只提供受限 profile？
  • ContextManager 首版直接移植上游算法，还是先做最小兼容接口？
  • 只读子 Agent 的最大并发和最大预算分别是多少？
  • 代码沙盒优先容器还是 microVM？网络默认是否完全关闭？
  • 是否要求兼容上游现有会话、技能和站点授权数据？
