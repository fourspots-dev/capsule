1. 版本规则

所有可发布产物使用严格的 A.B.C 三段版本。版本号是产品契约，不是日期、构建号或内部计数器。

段位何时增加示例重置规则
A 主版本不兼容变化：Session/协议迁移无法兼容、工具语义破坏、旧客户端失效、配置必须迁移1.4.2 → 2.0.0B、C 归零
B 次版本向后兼容的新 feature、新工具、新端点、新能力、新配置项1.4.2 → 1.5.0C 归零
C 修订版本向后兼容的 bugfix、小改动、性能修复、文档契约修正1.4.2 → 1.4.3不重置 A/B

一个发布只升一段

同时包含不兼容变化和新 feature 时，按最高影响升级 A，并重置低位。

开发分支不反复升版

同一需求分支使用一个目标版本；发布合并时只更新一次 package.json。

纯格式修改

不改契约、不改变行为的文档排版可不升版，但仍需关联一个工程需求或现有需求。

契约文档变化

如果设计改变了外部行为、工具协议或验收标准，按 feature 或 bugfix 升级对应版本。

单一版本源

  • 根 package.json.version 是当前产品版本的唯一来源。
  • 扩展、TUI、CLI 的构建产物从同一发布版本生成。
  • 发布时创建 annotated tag：vA.B.C。
  • 禁止使用 latest、final、日期等非语义版本作为正式发布。

2. 需求编号

所有新功能、重构、工程能力、重要 bugfix 和安全修复都必须先建立需求记录，再进入设计。

REQ-<AREA>-<NNN>

示例：
REQ-TUI-001       富终端 UI
REQ-PATCH-001     ContextPatch 工具协议
REQ-PATCH-002     Patch ToolPack 跨宿主演进
REQ-ENG-001       版本与需求追踪规范
REQ-GIT-014       Git 兼容修复
字段要求
id全局唯一、永不复用；创建后不因标题变化而改名
title面向用户或系统的可验收能力，不写实现细节
typefeature | bugfix | security | refactor | infrastructure | documentation
priorityP0 | P1 | P2 | P3
statusproposed → accepted → in_progress → implemented → verified → released
targetVersion目标 A.B.C；正式发布后不得修改
design设计文档路径和精确章节锚点
testDesign测试设计路径和精确章节锚点
acceptance可观察、可测试的完成条件
需求拆分原则：一个 REQ 必须有独立验收价值。跨多个宿主的同一能力属于一个 REQ；宿主适配差异作为同一 REQ 的验收项。需求范围发生不兼容变化时新建 REQ，并建立 Supersedes 关系。

历史兼容

已有的 FR-CODE-03、RICH-R13、PATCH-01 等标识保留为历史/子测试 ID。新需求统一使用 REQ-*；需求注册表可以记录 legacy aliases，但不得重复定义同一事实。

3. 设计与测试文档契约

设计文档必须说明

  • 问题、范围和非目标
  • 核心对象、接口和状态机
  • 模块交互与数据流
  • 失败、恢复、安全和兼容性
  • 测试可观察的验收结果

测试文档必须说明

  • 需求到测试 ID 的追踪矩阵
  • Unit / Contract / Integration / E2E 层级
  • 正常、边界、故障和状态空间
  • 测试 fixture、执行命令和证据
  • 发布阻断条件

文档放置与命名

功能较大：
docs/<area>/<REQ-ID>-design.html
docs/<area>/<REQ-ID>-testing.html

同一能力包含多个相关需求：
docs/<area>/vX.Y-design.html#<requirement-anchor>
docs/<area>/vX.Y-testing.html#<requirement-anchor>

小型 bugfix：
可复用所属模块的设计/测试文档，但必须提供精确章节锚点。

注册表保存的是稳定锚点，不保存“看某文档大概某处”。无设计或测试链接的需求不得进入 in_progress。

3.1 用户确认与实现门禁

accepted 只表示需求范围和目标被接受，不代表用户已经授权修改产品代码。每个需求必须记录详细设计状态和实现授权。

字段含义
designStatus: draft设计仍在编写，不可评审或实现
designStatus: review详细设计和测试设计已提交，等待用户确认
designStatus: approved用户确认详细设计，但仍不一定授权写代码
implementationAuthorized: true用户明确要求开始实现
Agent 不得自行把 designStatus 改为 approved，也不得自行设置 implementationAuthorized: true。“可以先做”“推进设计”不得解释为开始编码。

详细设计最低内容

  • 模块新增、修改和明确不得感知的边界。
  • 公共接口、Schema、错误码和不变量。
  • 对象归属、生命周期和状态机。
  • 端到端交互、取消、恢复和迁移路径。
  • 安全、审批、持久化和兼容策略。
  • 可拆分的实现切片和验收条件。

详细测试设计最低内容

  • 每个 FR 到测试 ID 的映射。
  • 具体 fixture、计划测试文件和命令。
  • 正常、边界、故障、安全和恢复用例。
  • 跨模块、跨执行面和架构边界测试。
  • 证据 Artifact、发布阻断和阶段门禁。

3.2 Architecture Decision Records

ADR 保存长期架构决策及原因，REQ 保存待交付的工作。一个 REQ 可以引用多个 Accepted ADR；ADR 可以关联多个 REQ。普通局部实现通常只需要 REQ。

必须创建 ADR

  • 模块边界或依赖方向变化。
  • 公共协议、持久化格式、信任模型和跨端契约。
  • 多个长期方案之间的选择。
  • 影响多个需求或执行面。
  • 替代旧 Accepted 决策。

状态与转换

  • proposed → accepted：用户确认，成为当前架构约束。
  • proposed → rejected：用户拒绝，保留替代方案证据。
  • accepted → superseded：新 Accepted ADR 替代旧决策。
  • accepted → deprecated：仍保留历史，但不再指导新设计。
  • rejected / superseded / deprecated：终态，不改回当前约束。
docs/adr/ADR-NNN-kebab-title.md
policy/adr-registry.json
docs/adr/README.md
docs/adr/template.md

Accepted ADR 不可删除或静默改写。只允许不改变语义的排版、链接或错字修订，并应在提交中说明；Decision、Invariants 或边界变化必须创建新 ADR。替代关系使用 Supersedes / Superseded by 双向引用。ADR Accepted 不等于实现授权，实现仍受 REQ 详细设计确认和用户授权门禁控制。

单一事实链：ADR 回答“为什么必须保持这条架构规则”，REQ 回答“要交付什么”，详细设计回答“具体怎样实现”，详细测试设计回答“怎样证明实现正确”。四者缺一不可，但只有 REQ 的 implementationAuthorized 能授予编码权限。
npm run adr:check

校验：
  ID 唯一、文件已注册且无孤立 ADR 文件
  文件名、正文标题、状态、日期、批准人和关联 REQ 与 registry 匹配
  必需章节齐全
  Accepted/Rejected 有用户批准和日期
  受影响 REQ 存在且 ADR 至少关联一个 REQ
  Supersede 双向对称且无循环

ADR 变更流程

1 · 识别模块边界、协议或长期选择变化
2 · Proposed新建不可复用 ID 和完整 ADR
3 · 关联连接受影响 REQ 与验证证据
4 · 确认用户批准或拒绝
5 · 落地REQ 详细设计引用 Accepted ADR
6 · 演进新 ADR 替代旧 ADR，不改写历史

4. 架构变更影响面

共享能力、协议、持久化模型、工具、客户端接口或跨宿主契约变更时，不能把“某个模块已实现”当作需求完成。设计文档必须提供影响面矩阵，逐项覆盖 Provider、Consumer、生命周期、持久化与迁移、UI/Prompt/ToolRegistry、降级与清理。

编码前

  • 列出所有会提供、组合、消费或持久化该能力的模块。
  • 每个 Consumer 标记 modify 及证据，或标记 none 及技术原因。
  • 说明旧路径和隐式 fallback 的删除或保留策略。
  • 列出端到端用户旅程，不只列类或接口。

禁止

  • Headless 已支持，但 TUI/Prompt/Verifier 仍走旧模型。
  • 为单个客户端复制 ToolPack 或 Schema。
  • 能力缺失时静默回退到通用 shell。
  • 把历史测试证据当成当前宿主证据。

标记为 architectureImpact: true 的需求，其 Design 必须包含 #architecture-impact。模板与检查清单位于 docs/requirements/architecture-change-contract.md。

5. 架构完整性与完成证据

测试设计必须把影响面矩阵转换成可执行证据，并为每个必需 Consumer 提供端到端验收。

层次必须证明
唯一实现共享 ToolPack/Schema/Composer，不存在平行业务实现
Provider成功、不可用、拒绝、故障、取消和版本不兼容
ConsumerHeadless/TUI/CLI/Chrome/Sandbox 等规定入口全部接通
一致性CapabilityReport、ToolRegistry、Prompt、UI 和 Verifier 使用同一能力事实
持久化Session、Artifact 和 Capsule 可恢复；环境变化使旧证据失效
迁移至少一条跨宿主用户旅程，导出、导入、运行和续跑有证据
清理Legacy 路径被删除，或保留原因与兼容测试明确

标记为 architectureImpact: true 的需求，其 Test Design 必须包含 #architecture-completeness。

6. 提交协议

提交标题使用 Conventional Commit 风格，并必须包含一个或多个 REQ-ID。

feat(REQ-PATCH-001): implement contextual patch protocol

Add ContextPatch parsing, unique context matching, version guards,
transactional rollback and a separate unified-diff tool.

Requirement: REQ-PATCH-001
Version: 0.2.0
Design: docs/production-coding-agent-detailed-design.html#patch-tool
Tests: docs/production-coding-agent-detailed-testing.html#patch
Test-Evidence: npm run check
字段约束
标题 typefeat | fix | refactor | perf | test | docs | build | ci | chore | revert
标题 scope一个或多个 REQ-*，逗号分隔
Requirement:与标题中的需求集合一致
Version:与提交时 package.json.version 一致
Design:至少一个存在的设计路径，可带锚点
Tests:至少一个存在的测试设计路径，可带锚点
Test-Evidence:明确命令或可复核证据，不写“已验证”空话
提交不能只写“update code”或只挂 issue 链接。一个提交可以完成多个需求，但每个需求都必须登记，并且设计/测试文档存在。

版本提交记录检索

git log --format='%h %s%n%(trailers:key=Requirement,valueonly)'
git log --grep='REQ-PATCH-001'
git log --format='%h %(trailers:key=Version,valueonly) %s'

7. 需求交付工作流

1. Intake建立 REQ，写验收和非目标
2. Design详细设计与对象接口
3. Test详细测试设计与追踪矩阵
4. Confirm用户确认设计并授权实现
5. Build实现，测试先行或同步
6. Verify自动检查、真实 E2E、证据
7. Release版本、tag、变更记录
  1. 需求登记后状态为 accepted，分配目标版本，详细设计状态从 draft 开始。
  2. 详细设计和详细测试提交后设为 designStatus: review。
  3. 用户确认后设为 approved，并显式设置 implementationAuthorized: true。
  4. 满足门禁后才能进入 in_progress 并开始代码实现。
  5. 实现提交必须携带需求与文档链接。
  6. 测试通过且验收项有证据后进入 verified。
  7. 发布时更新版本、CHANGELOG、annotated tag 和注册表状态。

状态约束

状态必要条件
proposed标题、目标、验收草案
accepted优先级、目标版本、详细 design/test 路径，designStatus: draft/review
in_progress用户确认，designStatus: approved，implementationAuthorized: true
implemented代码完成，至少相关测试通过
verified完整测试、E2E、性能和兼容门禁通过
released版本 tag 和 release record 存在

8. 发布与提交记录

  1. 确定本次发布最高影响：major / minor / patch。
  2. 更新 package.json 与 lockfile 的版本。
  3. 生成或更新 CHANGELOG.md，按 REQ 分组。
  4. 确认所有纳入的 REQ 状态为 verified。
  5. 创建 annotated tag：git tag -a vA.B.C -m "Release A.B.C"。
  6. 发布后将 REQ 状态改为 released。

7.1 AGENTS.md 强制入口

根目录 AGENTS.md 是 coding agent 的强制入口，负责汇总需求登记、设计与测试文档、版本升级、提交 trailers、验证和发布规则。子目录规则可以补充本目录特例，但不能放宽本文的版本、需求追踪和验收要求。

阻断条件：无 REQ、未知 REQ、设计或测试文档缺失、版本格式错误、提交 Version 与 package.json 不一致、缺少验证证据。

11. 本规范验收

  • 注册表中每个 REQ 都有唯一 ID、目标版本、Design、Tests、Design Status 和 Implementation Authorization。
  • 需求/设计/测试模板可以直接复制使用。
  • ADR 文件、注册表、正文元数据和受影响 REQ 完全一致，且没有未注册 ADR。
  • Accepted/Rejected ADR 有用户批准、完整章节和合法状态转换；Supersede 双向对称且无循环。
  • 标记 architectureImpact: true 的需求必须包含架构影响面和完整性证据锚点。
  • 未获用户确认和实现授权的 REQ 不能标记 in_progress。
  • commit hook 拒绝缺少 REQ、Version、Design、Tests 或 Test-Evidence 的提交。
  • hook 拒绝不存在的 REQ、文档路径和版本不一致。
  • npm run requirements:check 和 npm run adr:check 在正常检查链中执行。
  • 从一个需求请求到发布 tag 的完整流程可以按本文执行并复核。

机器可读注册表：policy/requirement-registry.json。需求状态以注册表为准，设计事实以设计文档为准，验收事实以测试文档和 CI 证据为准。
