模块化完善方案

把当前“可以组合”的能力推进为正式、可验证、可替换的模块契约。目标不是增加抽象数量，而是消除浏览器语义泄漏、统一 ToolPack/PromptProfile，并让 Chrome、TUI、Web 和批处理端共享稳定的 Core。

当前基线：179 个确定性测试 + 5 个 Chrome E2E 通过
现状依赖顺序1 WorkspacePort2 TargetPort3 Browser拆分4 ToolPack5 Prompt6 TUI7 组合根验收

1. 当前基础与缺口

已经完成

BrowserProvider、Chrome Workspace Registry、Chrome Prompt、Browser ToolPack 已移出 Core；Chrome RuntimeExtension、SessionAccessPort、ToolPack、PromptProfile 已建立；Core 有独立 tsconfig 和依赖边界扫描。

主要缺口

WorkspacePort 只存在结构相似的实现；BrowserProvider 仍过大；Skill/MCP/Subagent ToolPack 未统一；CLI Prompt 内联；TUI 只有边界没有实现；Chrome Runtime 组合根仍过重。

设计原则：Core 不导入 Adapter；Browser/TUI/Web 只实现自己的 Workspace 和 ToolPack；所有跨端数据使用不透明 ID、通用 Snapshot 和显式端口。

1 WorkspaceControlPort 正式化

当前 Chrome Registry 的接口形状与 Platform Contract 接近，但没有显式实现统一返回类型。需要把 Chrome 内部 group/tab 映射转换为不透明 WorkspaceActivation。

interface WorkspaceControlPort<Input> {
  resolve(input: Input): Promise<WorkspaceActivation>;
  create(input?: Input): Promise<WorkspaceActivation>;
  bind(sessionId: string, input: Input): Promise<WorkspaceActivation>;
  listTargets(sessionId: string): Promise<WorkspaceTarget[]>;
  assertTarget(sessionId: string, targetId: string): Promise<void>;
  release(sessionId: string): Promise<void>;
  clear(): Promise<void>;
}

实现要点

  • Chrome Registry 显式 implements WorkspaceControlPort<ChromeActivationInput>。
  • ChromeActivationInput 留在 Adapter，不进入 Core。
  • 返回 workspaceId、activeTargetId、generation；Chrome window/group/tab 字段只能作为 Adapter 附加字段。
  • Registry 只依赖 SessionAccessPort 和 BrowserTargetPort。
  • 迁移 v1 tab binding 到 group/tab 双作用域，迁移必须幂等。
完成标准：ChromeWorkspace 可以被 Platform Contract 消费；TUI 可以用同一接口实现完全不同的 Standalone Workspace。

2 WorkspaceTargetControl 接入 Browser ToolPack

Agent 工具不应直接依赖 ChromeBrowserProvider。new_tab、switch_tab、list_targets 通过 WorkspaceTargetControl 操作当前 Workspace。

interface WorkspaceTargetControl {
  createTarget(sessionId: string, spec?: Record<string, unknown>): Promise<WorkspaceTarget>;
  activateTarget(sessionId: string, targetId: string): Promise<void>;
  listTargets(sessionId: string): Promise<WorkspaceTarget[]>;
  assertTarget(sessionId: string, targetId: string): Promise<void>;
}
  • Chrome 实现将 target 映射为 tab，TUI 可映射为 pane。
  • 组外 target 返回 TARGET_OUTSIDE_WORKSPACE。
  • 创建 target 时先完成 Workspace 绑定，再激活，避免 tabs.onActivated 竞态。
  • Browser ToolPack 只看到 WorkspaceTarget，不读取 Chrome groupId。

3 BrowserProvider 能力拆分

当前 BrowserProvider 同时包含标签、DOM、CDP、网络、PDF、上传和 Dialog，职责过宽。建议拆成小接口，并由 ChromeBrowserAdapter 组合实现。

BrowserTargetProvider

list/create/activate/group/assert/release target。

BrowserPageReader

snapshot/readText/find/evaluate/read-only network。

BrowserPageActor

click/fill/select/drag/scroll/upload/dialog/navigate。

BrowserArtifactProvider

screenshot/print PDF/artifact capture。

BrowserDebugPort

受控 CDP/Frame/Network 高级能力。

BrowserProviderFacade

兼容旧调用，组合以上接口。

interface BrowserToolPackDependencies {
  targets: WorkspaceTargetControl;
  reader: BrowserPageReader;
  actor: BrowserPageActor;
  artifacts?: BrowserArtifactProvider;
}

迁移时保留 BrowserProvider facade，避免一次性改完所有工具和测试；然后逐个 ToolPack 切换到小接口。

4 所有 ToolPack 统一

目前只有 Browser ToolPack 正式使用 ToolPack 接口，Skill、MCP、Subagent、Sandbox 仍在组合根手工注册。需要统一为可枚举、可筛选、可诊断的模块。

interface ToolPack {
  id: string;
  requires?: string[];
  register(context: ToolPackContext): ToolRegistration[];
}
ToolPack能力适用端
browser页面读取、交互、标签 WorkspaceChrome / Web Agent
sandbox文件、命令、PTY、测试TUI / CLI
subagentspawn/send/wait/stop/list所有允许子 Agent 的端
skills用户 Skills 调用Chrome / TUI / Web
mcpMCP 工具代理支持网络和授权的端
extension用户/项目扩展工具按宿主支持

ToolPack 需要声明能力、风险、所需 Context 和释放方法；注册失败不应导致整个 Runtime 无法启动，应产生诊断项。

5 PromptProfile 全端统一

Chrome 已使用 PromptProfile，CLI 仍内联提示词。需要把 Prompt 从运行逻辑中完全拆开。

interface PromptProfile {
  id: string;
  build(context: {
    profile?: ResolvedAgentProfile;
    skills: readonly SkillDefinition[];
    workspace?: WorkspaceDescriptor;
  }): string;
}
  • ChromePrompt、TuiPrompt、CodingPrompt、ReviewPrompt 可独立组合。
  • Profile instructions 和 Skills 目录只通过 PromptProfile 注入。
  • 禁止在 SessionRuntime 内判断“是否 Chrome”。
  • Prompt 测试验证包含必要规则且不泄漏其他端工具。

6 TUI Adapter

TUI 是验证 Core 边界是否真正成立的关键。首版只需要单 Workspace、文件/Sandbox 工具和文本项目，不实现标签组。

TerminalWorkspace implements WorkspaceControlPort<TerminalInput> {
  resolve() → 当前终端 Session
  create()  → 新 Terminal Workspace
  listTargets() → [{ id: "terminal", kind: "terminal" }]
}

首版范围

输入、流式输出、Reasoning、工具状态、审批、History。

明确非目标

Chrome tab/group、Browser ToolPack、Screenshot UI。

TUI 构建产物不得包含 chrome.tabs、BrowserProvider、Chrome RuntimeExtension 或 Side Panel 资源。

7 Runtime 组合根重构

ChromeRuntime 当前同时负责配置、存储、模型、Skills、MCP、Subagent、Browser、Workspace、Gateway 和生命周期。拆成可测试的组合函数。

createCoreRuntime({
  model, sessionStore, tools, approval,
  clock, ids, prompt
}) → CoreRuntimeBundle
composeChrome({
  core, browser, workspace, runtimeExtension
}) → ChromeRuntimeBundle
wireGateway({
  bundle, protocol: ChromeProtocol
}) → RunningGateway
  • 配置解析独立。
  • ToolPack 和 Prompt 独立装配。
  • Subagent Driver 可注入 WorkspaceFactory。
  • MCP/Skills 启动失败进入诊断，不阻塞 Core。
  • dispose 按依赖逆序执行。
