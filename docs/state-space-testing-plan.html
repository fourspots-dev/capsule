TINYAI / STATE-SPACE TESTING / DESIGN

状态空间测试方案

用“有界穷举 + 参考模型 + 并发模型检查 + Chrome 故障注入 + UI 状态组合 + 代表性 E2E”覆盖 Coding Agent 和浏览器 Workspace 的关键行为，而不是依赖不断增加顺序手写测试。

当前基线：187 个确定性测试5 个 Chrome E2E首批参考模型与故障注入已实现覆盖率 55.86% statements
目标状态模型不变量六级测试顺序矩阵故障注入UI组合判定与复现CI门禁当前缺口

1. 目标与边界

要解决的问题

  • 标签关闭、激活、分组和 Runtime 重载的事件交错。
  • Session、Workspace Binding 和 Projection 的一致性。
  • 快速切换、审批、队列和后台任务的组合。
  • 测试失败可以稳定重放。

不追求的目标

  • 穷举真实网页 DOM 和所有外部网络行为。
  • 穷举任意长度模型输出和用户输入。
  • 在 CI 中全量运行所有 Chrome/OS 组合。
  • 用行覆盖率替代行为判断。
核心策略：对控制面做有限抽象和有界穷举；对输入空间做属性测试；对真实浏览器只保留代表性 E2E 和故障注入。

首批实现状态：Workspace 参考模型、固定事件顺序矩阵、关闭/延迟/分组失败故障注入、RuntimeExtension 事件、Projection 组合和 V8 覆盖率门禁已经接入；TLA+、深度 soak、mutation testing 仍是后续阶段。

2. 被测状态模型

2.1 浏览器 Workspace 状态

Window
  tabs: 0..3
  activeTabId: one of tabs or none
Tab
  alive: true | false
  group: none | G1 | G2
Binding
  scope: none | tab | group
  session: S1 | S2 | historical
  activeTarget: tab
Session
  lifecycle: unloaded | ready | reloading | stopped
  task: idle | running | waiting | completed | failed | cancelled
UI
  currentSession: S1 | S2 | none
  pendingActivation: 0..2
  pendingApproval: yes | no
  queue: 0..2

边界规模固定为最多 3 个 Tab、2 个 Group、2 个 Session。通过对称性约简，避免标签 ID 造成无意义的状态爆炸。

2.2 事件域

类别事件说明
Chromeactivate, close, group, ungroup, move-window标签存在性和成员关系变化
Workspaceresolve, create, bind, promote, release, clearSession 映射变化
Runtimereload, cold-load, delete-session, stop-task生命周期变化
Agentnew-tab, switch-tab, read, write, approval工具和目标操作
UIswitch-tab, history-open, reconnect, render客户端状态变化

3. 必须始终成立的不变量

ID不变量失败含义
INV-01一个 Tab 最多属于一个有效 Binding。同一标签串到两个会话。
INV-02一个 Group 最多绑定一个 Workspace Session。组内对话分裂。
INV-03Group Binding 的成员必须全部真实存在且 groupId 一致。幽灵标签或错误目标。
INV-04Standalone Binding 不得指向已关闭 Tab。BROWSER_TAB_NOT_FOUND 等脏映射。
INV-05Active Target 必须是当前 Workspace 的成员。Agent 越界操作。
INV-06Session 不能同时绑定两个互不一致的 active tabs。并发切换覆盖。
INV-07UI 最终只订阅最后活动 Scope 的 Projection。旧会话覆盖新会话。
INV-08旧激活事件不得覆盖更新 generations 的状态。竞态回退。
INV-09关闭最后 Group 成员必须清理 Group Binding。groupId 复用导致串话。
INV-10Runtime 重建后有效 Tab 必须恢复原 Session。对话丢失或重复。
INV-11只有显式 new_tab 才能创建浏览器 Tab。自动打开空白页。
INV-12审批、队列和任务状态不能在切换时串 Session。跨标签数据泄漏。

4. 六级测试结构

L1

纯状态机穷举

没有浏览器和异步，只验证有限转换与终态。

范围

Session Lifecycle、Task、Input Ledger、Command Inbox、Binding 状态。

方法

枚举所有 State × Event；断言只允许的转换、终态不可离开、重复事件幂等。

产出

转换矩阵、非法转换表、覆盖率报告。

完成标准

所有已声明状态和事件均至少被枚举；未建模事件必须显式失败。

L2

Workspace 参考模型与有界穷举

用独立内存模型判断实际 Registry 是否始终等价。

参考模型

维护 tabs、groups、tabBindings、groupBindings、activeTab、sessions。

序列规模

1-3 个 Tab、1-2 个 Group、2 个 Session，事件序列长度 1-5。

生成方式

先做短序列穷举；再做 fast-check stateful property 随机序列 500-2000 步。

断言频率

每个事件后校验全部 INV-01 至 INV-12，而不是只检查最终结果。

L3

并发事件与模型检查

验证事件顺序，而非业务算法。

TLA+

建模 Tab、Group、Binding、Session、reload 和 activate/close 事件。

目标

检查无死锁、无双绑定、无过期激活覆盖、无残留 Group Binding。

限制

模型只保留控制面字段，不模拟 DOM、模型 token 或真实 Chrome 实现。

持久化

把验证通过的模型和失败 trace 纳入仓库，作为实现对照。

L4

Chrome API 故障注入

在 Adapter 边界模拟延迟、失败和状态漂移。

注入点

tabs.get/create/update/group/ungroup/remove、onActivated/onRemoved/onDetached、debugger.attach、tabGroups.update。

结果域

success、delay、not-found、throw、stale、partial success。

时序

每个操作前后允许事件晚到、重复和反序。

断言

错误可观察、映射可清理、UI 不暴露内部竞态、后续操作可恢复。

L5

Projection 与 UI 状态组合

覆盖 Render Model 输入组合和切换竞态。

维度

task、queue、approval、reasoning、tool family、child、error、session generation。

组合策略

对高风险维度做全组合，对纯样式维度做 pairwise/representative。

断言

无错位、无跨会话状态、旧帧不覆盖新帧、审批优先于 Thinking。

DOM

语义快照 + 关键截图；不以像素截图替代状态逻辑。

L6

真实 Chrome E2E 与长时间运行

保留最有价值的高风险路径，并加入 soak test。

日常 E2E

建组、组外独立、关闭活动标签、Runtime reload、审批、History、清理。

Soak

连续切换/关闭/重开标签 1000 次，检查 Session、监听器、Debugger 和内存。

故障

Service Worker 重启、Offscreen 重启、网络断开、模型断流。

发布门禁

成功路径不足以发布；关键不变量和资源清理必须通过。

5. 事件顺序矩阵

ID事件序列必须验证
ORD-01activate(A) → activate(B)A 的晚到结果不能覆盖 B
ORD-02activate(A) → close(A)映射删除，不显示内部错误
ORD-03close(A) → activate(A)旧事件幂等忽略
ORD-04close(A) → activate(B)切换 B，不引用 A
ORD-05group(A,B) → activate(B)同一 Group Session
ORD-06ungroup(B) → activate(B)B 获得独立 Session
ORD-07reload_runtime → activate(A)恢复 A 的原 Session
ORD-08activate(B) → reload_runtime最终恢复 B
ORD-09close(A) → onRemoved(A) → activate(B)不出现 BROWSER_TAB_NOT_FOUND
ORD-10new_tab(A) → activate(new) → close(original)Group 和 active target 一致

6. Chrome 故障注入细节

故障模拟预期行为
TAB_DISAPPEARSgetTab 返回 null清除独立 Binding；不继续操作
TAB_SLOW_VISIBLEcreate 后延迟可见有界重试，不创建第二个 Tab
GROUP_FAILEDtabs.group 抛错Session 保留，Workspace 状态不半写
GROUP_TITLE_FAILEDtabGroups.update 失败不影响核心 Workspace
ACTIVATE_LATE旧 onActivated 晚到generation 拒绝旧结果
REMOVE_DUPLICATEonRemoved 重复触发forget 幂等
DEBUGGER_DETACHEDdetach 报 not attached清理成功，不阻断 reload
GROUP_ID_REUSED旧 groupId 被新组复用成员交集校验后新建 Session

8. 判定、复现与失败产物

双重判定

参考模型必须与真实状态逐步一致；同时执行全部不变量检查。

确定性

时钟、随机数、Chrome 回调、模型输出和 ID 必须可注入。

失败复现

输出 seed、事件序列、每步前后状态、Chrome API 结果和 UI generation。

最小化

fast-check 自动 shrink 到最短失败序列；不可 shrink 的 E2E 保留完整 trace。

Failure artifact:
{
  suite, seed, failureInvariant,
  initialSnapshot,
  events: [{ method, args, outcome, before, after }],
  projectionRevision,
  browserTabs,
  uiGeneration,
  consoleAndRuntimeLogs
}
任何新发现的竞态必须加入固定回归 seed 和一条可读的 E2E/Integration trace，不能只依赖随机测试“以后可能跑到”。

10. 当前覆盖评估与实施顺序

区域现状优先级
Task/Input/Lifecycle属性覆盖较好保持
TabSessionRegistry顺序场景P0：参考模型
Chrome 事件交错覆盖不足P0：顺序矩阵 + 故障注入
UI Projection 切换若干 E2EP1：状态组合
Persistence/Recovery基础覆盖P1：故障恢复
Sandbox平台正常路径P1：异常与 soak
代码/分支覆盖率当前未配置P1：coverage-v8
Mutation testing未配置P2：Nightly

推荐实施顺序

  1. 建立 Workspace 纯参考模型和 INV-01 至 INV-12。
  2. 完成 3 Tab / 2 Group / 5 步事件的有界穷举。
  3. 加入 Chrome API 故障注入和固定顺序矩阵。
  4. 建立 Projection/UI 组合生成器。
  5. 接入覆盖率、mutation 和夜间 soak。
  6. 引入 TLA+ 验证并发控制面。
完成标准：不只是“测试数量增加”，而是新竞态能被状态生成器或模型检查主动发现；失败能靠 seed/trace 稳定重放；关键不变量在每一步事件后都成立。
