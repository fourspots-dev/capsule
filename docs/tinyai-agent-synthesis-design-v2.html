SYNTHESIS DESIGN · REVIEW v0.2

以成熟行为为基线，重建可扩展且可控的 Agent

新版设计融合 Pi 1.4 的 Agent Harness 抽象、上游 Browser Agent 的产品级行为，以及 tinyai 的持久任务、能力权限与沙盒边界。它不是再一次从头发明 Agent，而是明确回答：哪些行为直接借鉴，哪些需要适配，哪些只作为风险参考。

01

三源融合与取舍

三个参考系统解决的问题不同，融合时必须区分机制价值和产品行为。

Pi Coding Agent

最小 Harness

学习 AgentMessage、事件流、Tool 契约、Session Tree、Compaction、Extensions、RPC/SDK 和统一接口。

  • 直接借鉴：循环与事件模型、工具协议、压缩切点
  • 适配采用：扩展机制、Code Mode、RPC
  • 风险参考：默认无权限沙盒、扩展同进程
Browser Agent

产品级浏览器行为

学习后台会话循环、标签组、页面工具、自动压缩、子 Agent、审批恢复、模型降级和真机回归。

  • 直接借鉴：页面工具细节、子 Agent 事件、真实 Chrome 测试
  • 适配采用：域名授权、模型恢复、持久时间线
  • 风险参考：大模块、完全授权模式
tinyai Kernel

持久与安全边界

保留 TaskRuntime、TaskGraph、能力策略、事件日志、Artifact、Workspace 和 SandboxProvider。

  • 核心差异：任务租约、审批 digest、来源标签
  • 核心差异：子 Agent 权限求交集
  • 核心差异：外部受限执行环境
不能混为一谈

Pi 的 Session Tree 是上下文历史结构，TaskRuntime 是执行状态机；两者必须关联但不能合并成一个对象。否则 branching、恢复和审批会把对话历史与运行控制状态污染在一起。

原则一

Harness 不等于 Runtime

Agent Harness 负责消息、循环和工具交互；TaskRuntime 负责持久生命周期和权限预算。

原则二

SessionTree 不等于 TaskGraph

会话树表达上下文与分支；任务图表达执行、所有权、等待和状态恢复。

原则三

事件不等于 UI

事件是事实，Projection 是可重建视图；UI 不能直接修改 Agent 或工具状态。

05

Control Plane / UI Projection

界面是所有 AgentSession 事件的消费者，不是 Agent 状态的第二份事实源。

M0

Control Plane / UI Projection

命令、事件投影、审批、计划与 artifact 展示

P0 · Interface
PI-A7UP-A1TL-A1

设计要点

  • 统一 Command：prompt、steer、followUp、abort、approve、pause、cancel。
  • 订阅 AgentEvent，以 snapshot + afterSeq 支持断线重连和去重。
  • 流式文本仅作为临时投影；message_end 是权威完成事件。
  • 审批卡显示动作、资源、风险、digest 和过期时间。
  • UI 不直接调用 Provider、Tool 或 SessionManager。

核心对象

interface UICommand {
  type: "prompt" | "steer" | "followUp" | "abort"
      | "approve" | "pause" | "resume" | "cancel";
  taskId: string;
  payload?: unknown;
}

interface EventSubscription {
  taskId: string;
  afterSeq: number;
  onSnapshot(value: TaskSnapshot): void;
  onEvent(event: AgentEvent): void;
}

交互

UI 发送命令；TaskRuntime 提交事件；Projection 重建消息时间线、工具卡、审批和 artifact。RPC、SDK、TUI 和 Chrome Side Panel 复用同一事件契约。

直接借鉴基线

Pi 的同一 Session 驱动 TUI/Print/JSON/RPC/SDK，以及上游 Browser Agent 的端口广播和时间线投影。

验收

  • 断线重连不丢事件、不重复消息。
  • message_end 前不显示“已完成”。
  • 所有审批与 artifact 可以从事件重建。
06

AgentSession / AgentLoop

以 Pi 的 Harness 作为对话执行骨架，向上提供稳定命令，向下连接模型、工具和压缩。

M1

AgentSession / AgentLoop

Turn 循环、消息事件、Steering 与 Follow-up

P0 · Borrow core
PI-A1PI-A2PI-A4

设计要点

  • AgentMessage 与 LLM Message 分离，自定义 UI/状态消息不直接发送模型。
  • 事件区分 agent/turn/message/tool 四级生命周期。
  • 支持 steer 与 followUp 两种排队语义。
  • 提供 prepareRequest、prepareNextTurn、finishTurn、before/afterToolCall hooks。
  • 一个 run 可能包含多个 turn；只有 agent_settled 表示自动工作结束。
  • AgentSession 不直接持久化 TaskGraph，通过 TaskRuntime 协调。

核心对象

interface AgentSession {
  prompt(input: PromptInput): Promise<void>;
  steer(input: UserInput): Promise<"queued" | "handled">;
  followUp(input: UserInput): Promise<"queued" | "handled">;
  abort(): Promise<void>;
  waitForIdle(): Promise<void>;
  subscribe(listener: (event: AgentEvent) => void): Unsubscribe;
}

type AgentMessage = LlmMessage | CustomAppMessage;

交互

prompt 创建 run；loop 每个 turn 调用 ContextManager、ModelGateway、ToolExecutor。Steering 在当前工具批次后进入，Follow-up 只在自然停止前进入。所有事件交给 Runtime 持久化。

行为基线

PI-A1/PI-A2 直接借鉴：事件类型、消息边界、队列语义和 hook 顺序。需要调整的是把 AgentSession 的 finalized events 接入 TaskRuntime，而不是仅依赖 JSONL append。

验收

  • 工具结果按模型源顺序进入 transcript。
  • Steering 不跳过当前 assistant 已发出的工具。
  • Abort 后不再产生新模型或工具请求。
  • 自定义消息可持久化但不会未经转换发送模型。
07

TaskRuntime / TaskGraph

负责“任务是否还能继续、谁有权继续、预算是否足够”，不负责组织对话内容。

M2

TaskRuntime / TaskGraph

任务状态、租约、预算、等待与恢复

P0 · Critical
TL-A1PI-A9UP-A1

设计要点

  • TaskStatus 覆盖 queued/running/waiting/paused/completed/failed/cancelled。
  • 同一 Task 只有一个 fencing lease 写入者。
  • 一个 task 指向上游 SessionTree head，不复制全部消息。
  • 模型、工具、审批、人工等待和子任务都是显式状态。
  • 任务图记录父子所有权、等待策略和 background 标记。
  • 预算覆盖步骤、token、费用、wall time 和子任务总量。

核心对象

interface TaskRecord {
  id: string;
  parentId?: string;
  kind: "run" | "tool" | "compaction" | "subagent";
  status: TaskStatus;
  revision: number;
  sessionId: string;
  sessionHeadId: string | null;
  budget: TaskBudget;
  ownership: "conversation" | "task" | "background";
}

interface TaskGraphNode {
  taskId: string;
  ownerTaskId?: string;
  status: TaskStatus;
  waitingOn: string[];
  background: boolean;
}

交互

AgentSession 启动 run 时向 Runtime 领取 lease；Runtime 记录 turn/tool/approval 状态。切断 SSE、UI 关闭或进程重启后，Runtime 根据 snapshot、pending task 和 SessionTree head 决定恢复。

行为基线

TL-A1 原创补强；PI-A9 适配采用 pi-durable 的原子提交、Task Graph、child ownership 和 crash recovery，但暂不依赖其实验 API。上游的 queue/running/abort 是 P0 行为下限。

验收

  • 旧 lease 写入被拒绝。
  • 重启后 resume 不重复已确认副作用。
  • 父任务取消终止所有 owned child；background 显式例外。
  • 预算耗尽进入 paused 并保留恢复信息。
08

SessionTree / Repository

基于 Pi 的 JSONL 树，但通过 Storage Adapter 同时支持浏览器 IndexedDB、SQLite 和测试内存。

M3

SessionTree / Repository

会话历史、分支、上下文重建与回放

P0 · Adapt Pi
PI-A4PI-A5UP-A1TL-A1

设计要点

  • 每个 SessionEntry 带 id、parentId、type、timestamp。
  • active leaf 决定模型上下文；分支不删除历史。
  • Entry 类型包括 message、model change、usage、compaction、branch summary、context edit、custom。
  • 上下文重建时应用最新 compaction 和 context_edit。
  • 原始 SessionTree 用于 UI、导出和审计；模型投影可以不同。
  • TaskGraph 只引用 SessionTree，不复制消息正文。

核心对象

interface SessionEntry {
  id: string;
  parentId: string | null;
  type: "message" | "compaction" | "branch_summary"
      | "context_edit" | "custom" | "usage";
  timestamp: string;
  data: unknown;
}

interface SessionTreeStore {
  append(entry: SessionEntry): Promise<void>;
  setActiveLeaf(sessionId: string, entryId: string): Promise<void>;
  branch(sessionId: string, fromEntryId: string): Promise<SessionBranch>;
  project(sessionId: string, leafId: string): Promise<ModelContext>;
}

交互

AgentSession 完成 message 后 append；ContextManager 读取 active branch 并应用 compaction/context edits；UI 从同一树渲染完整历史和分支。Fork 只改变 leaf 或父会话，不复制无关运行状态。

行为基线

PI-A4 适配采用：保留 JSONL 树、分支、fork/clone、context edits；移除 Node-only 路径假设。持久后端应抽象为 Memory、IndexedDB、SQLite、JSONL。

验收

  • 切回旧节点后旧分支完整保留。
  • 分支上下文只包含当前路径。
  • context edit 不改变原始历史。
  • 旧 session 版本可以迁移或明确拒绝。
09

ModelGateway

保留 Pi 的 Provider 抽象和上游的容错细节，将协议差异收敛为一套内部事件。

M4

ModelGateway

多 Provider、流式事件、Auth、Retry 和模型恢复

P0 · Borrow behavior
PI-A1UP-A2UP-A6

设计要点

  • OpenAI completion/responses、Anthropic messages、Google 等统一为 ModelEvent。
  • 动态 Auth 在每次请求前解析，支持 OAuth 和短时 Token。
  • usage 统一 input/output/cache/cost 并落入独立 Entry。
  • 429、连接超时、上下文溢出、内容过滤、媒体过大分别分类。
  • 模型切换保留 from/to、原因和 usage 连续性。
  • stream 失败通过结束事件返回，不抛出半途丢失的异常。

核心契约

interface ModelGateway {
  stream(request: ModelRequest, signal: AbortSignal): AsyncIterable<ModelEvent>;
  resolveAuth(provider: string): Promise<AuthResult | null>;
  discoverModels(provider: string): Promise<ModelDescriptor[]>;
  resolveRecovery(error: ModelError, task: TaskSnapshot): Promise<ModelTarget | null>;
}

type ModelEvent =
  | { type: "text_delta"; text: string }
  | { type: "thinking_delta"; text: string }
  | { type: "tool_call_delta"; index: number; delta: unknown }
  | { type: "usage"; usage: Usage }
  | { type: "finish"; reason: StopReason }
  | { type: "error"; error: StructuredError };

交互

AgentSession 发送标准化 transcript；ModelGateway 注入 Auth 和 context limit，产生模型事件。ContextManager 处理 overflow；TaskRuntime 记录 retry 或 model-change event。

行为基线

直接借鉴 Pi 的 pi-ai Provider 抽象；直接借鉴上游的 retry、模型切换、媒体降级和错误分类。区别是 usage 和 recovery 统一进入 Task EventLog。

验收

  • Provider fixture 产生一致内部事件。
  • OAuth 过期时刷新或给出可操作错误。
  • 模型恢复后 task ownership 与上下文不变。
  • 密钥不进入事件、trace 或 UI。
10

ContextManager / Compaction

基于 Pi 的 SessionTree 压缩规则，并把大结果治理为 artifact。

M5

ContextManager / Compaction

Token 预算、压缩切点、溢出恢复和 Artifact 引用

P0 · Port first
PI-A5UP-A2TL-A1

设计要点

  • 压缩阈值使用 contextWindow - reserveTokens，不依赖固定百分比。
  • 保留最近 user-message spans，默认约 20k token，可按模型覆盖。
  • 有效切点只允许 user/assistant/bash/custom 消息，绝不切开 tool call/result。
  • 压缩追加 CompactionEntry，记录 summary、firstKeptEntryId、tokensBefore、usage。
  • overflow 或 length stop 最多自动恢复一次。
  • 超大输出先进入 ArtifactStore，再以引用进入上下文。

核心对象

interface ContextPlan {
  system: Message[];
  taskState: TaskState;
  retainedHistory: AgentMessage[];
  observations: ObservationRef[];
  reserveTokens: number;
}

interface CompactionEntry extends SessionEntry {
  type: "compaction";
  summary: string;
  firstKeptEntryId: string;
  tokensBefore: number;
  usage?: Usage;
  details?: {
    readFiles: string[];
    modifiedFiles: string[];
  };
}

交互

每次模型请求前从 active branch 构建 projection；达到阈值时 append compaction 后重建 projection。Provider overflow 时丢弃失败 attempt 的 model context、压缩并 retry once。压缩时 TaskRuntime 进入 waiting_compaction。

行为基线

PI-A5 直接借鉴：切点、保留边界、split user span、迭代摘要、usage 记录、overflow 顺序。UP-A2 直接借鉴：媒体降级和模型切换。新增 artifact 引用和来源标签。

验收

  • 压缩后 tool call/result 不拆开。
  • 重复压缩累计保留边界。
  • 原始历史仍可导出和搜索。
  • 压缩失败不破坏现有 SessionTree。

ToolRegistry / ToolExecutor

以 Pi 的 Tool 契约作为内核接口，以我们的幂等账本和权限闸门补强副作用恢复。

M6

ToolRegistry / ToolExecutor

Schema、并发、流式结果、取消、重放与副作用

P0 · Core borrow
PI-A3UP-A1UP-A5TL-A1

设计要点

  • 输入 schema 校验后才允许 beforeToolCall。
  • 工具结果分 content、details、structuredContent、usage，可流式 update。
  • executionMode 支持 parallel/sequential；一处 sequential 则整批串行。
  • 工具声明 replay: never|safe，执行器另生成 idempotency key。
  • 文件写入按 canonical path 加 mutation queue。
  • shell 输出按行/字节截断，完整输出保存到 artifact。
  • 工具输出命名 read/bash/edit/write，扩展工具使用 namespace。

核心契约

interface ToolDefinition<I, O> {
  name: string;
  label: string;
  parameters: Schema<I>;
  outputSchema?: Schema<O>;
  executionMode?: "parallel" | "sequential";
  replay: "never" | "safe";
  execute(
    callId: string,
    input: I,
    signal: AbortSignal,
    onUpdate: (partial: ToolUpdate) => void,
    ctx: ToolContext
  ): Promise<ToolOutcome<O>>;
}

interface ToolOutcome<O> {
  content: ContentBlock[];
  details: unknown;
  structuredContent?: O;
  isError?: boolean;
  artifactRefs?: string[];
  terminate?: boolean;
}

交互

AgentLoop 预检所有 calls；PolicyEngine 做 allow/ask/deny；ToolExecutor 路由 Provider，记录 start/update/end，按模型源顺序写 ToolResult Message。

行为基线

PI-A3 直接借鉴：schema、details/structuredContent、并发模式、file mutation queue、输出截断和 artifact 路径。新增统一 side-effect ledger 与 capability effect 声明。

验收

  • 非法参数不执行工具。
  • 并行结果事件按完成顺序、持久消息按源顺序。
  • 同一文件写不并发覆盖。
  • 取消后底层操作在可测时间内停止。
  • safe replay 不重复副作用，未知状态进入人工确认。

Extensions / ResourceLoader

工具、命令、Skills、Prompts、Themes、Provider 和 Hooks

P0/P1 · Adapt

设计要点

  • Manifest 固定 name、version、permissions、resources、entrypoints。
  • ResourceLoader 统一发现 extension、skill、prompt、theme、provider。
  • Skill 只注入名称、描述和路径，正文按需读取。

interface ExtensionManifest {

交互

行为基线

PI-A6 适配采用：资源发现、注册 API、hook 组合、热重载、Skills 按需加载。不直接复制 PI-A8：Pi extensions 在宿主进程全权限运行，目标设计必须显式 capability 和隔离边界。

验收

  • 未授权扩展不能注册高权限工具。
  • 热重载不中断正在执行的旧调用。
  • Skill 正文不在启动时全部注入上下文。
  • 扩展错误有稳定 diagnostics 且能回滚。

M8

PolicyEngine / ApprovalService

能力策略、风险、动作摘要与可恢复审批

P0 · Security critical
UP-A4PI-A8TL-A2

设计要点

  • PolicyEngine 只返回 allow/ask/deny，不直接弹 UI。
  • 审批绑定 taskId、revision、action digest、目标资源和 TTL。
  • 站点授权作为 UX profile 保留，但不能绕过能力硬拒绝。

interface NormalizedAction {

  target: string;

type PolicyDecision =
  | { type: "allow"; reason: string }

行为基线

UP-A4 适配采用：保留域名动作授权、挂起审批对账和“允许本站”交互。PI-A8 只作风险参考：不能把项目信任或编辑器确认当安全边界。

验收

  • 修改工具参数后旧审批失效。
  • 审批跨重启仍然可见并可以继续。
  • 站点永久授权不能绕过硬拒绝。
  • 子 Agent 无法调用父级未授权能力。

SubagentCoordinator

P1 · Adapt + govern
UP-A3PI-A9TL-A1TL-A2

设计要点

Workspace / SandboxProvider

P2 · Future
PI-A3PI-A8TL-A3

设计要点

  • 整个工作区只有 workspace root 可写，根文件系统只读。
  • 文件、patch、search、git、test、process 都成为明确能力。

  • 路径穿越和 symlink 逃逸被拒绝。

验收标准

每条验收都必须能够由自动化 fixture 或真机测试证明。

Harness

  • AgentMessage 与模型消息边界正确。
  • Steering/Follow-up 时序与暂停点正确。
  • 工具事件完成顺序和持久源顺序区分。
  • 自定义消息不会未经转换发送模型。
  • abort 在模型、工具、压缩和子任务间传播。

Session & Context

  • SessionTree 分支不删除历史。
  • 压缩追加 Entry 且使用正确切点。
  • overflow 只自动恢复一次。
  • 大输出转为 artifact 引用。
  • 旧 session 可迁移或明确拒绝。

Task & Policy

  • TaskGraph 可跨重启恢复。
  • 旧 lease 写入被拒绝。
  • 审批 digest/revision/TTL 绑定。
  • 子 Agent 权限无法提升。
  • 副作用有幂等键和审计记录。

Execution & Test

  • Browser 工具行为通过上游 fixture。
  • Provider retry/fallback 可重复测试。
  • Sandbox 路径/网络/资源逃逸测试通过。
  • 真机 smoke 覆盖 SW 重启和审批恢复。
  • 评测报告包含成本、延迟和副作用。
需要在评审中确认的决策
  • 直接依赖 Pi Agent Core，还是仅在接口与测试层面兼容？
  • SessionTree 首版采用 JSONL、IndexedDB，还是后端数据库？
  • 是否允许扩展在扩展进程运行，还是必须进入 Worker/Sandbox？
  • 子 Agent 首版并发是 1 还是 2？只读权限是否足够？
  • 是否保留上游“完全授权”模式，还是改为受限 profile？
  • Coding Sandbox 优先容器还是 microVM，Windows 支持如何处理？

最终设计原则

Pi 提供 Agent Harness 的结构和工具/会话行为；上游 Browser Agent 提供产品级执行与恢复基线；tinyai 补充 TaskGraph、能力权限和外部沙盒。实现时以这三层职责为准，不再把任何单一参考工程整体照搬。
