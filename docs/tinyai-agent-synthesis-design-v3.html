DETAILED DESIGN · v0.3

一个权威运行时，三种界面，两层执行边界

本版把 Pi 的 Agent Harness、ZCode 的产品运行时和 Browser Agent 的浏览器行为合并成一套可实现设计：每个 workspace 只有权威 Agent Runtime；UI 基于封闭 Projection 渲染；所有写操作通过 Command/ACK；子 Agent 由通用 Profile 定义，而不是固定角色枚举。

设计版本 v0.3 ZCode 基线 3.17.1 Pi 基线 1.4.0 Browser 基线 0.15.1 开发状态 待评审
本版核心决策

“会话历史”“任务执行”“实例生命周期”“UI 投影”必须分别建模。任何 UI、Host 或子 Agent 都不能成为第二份权威状态。

01

来源与设计取舍

本版不是功能堆叠，而是按职责吸收三个系统的优点，同时保留 tinyai 的权限和沙盒目标。

ZCode

产品运行时

吸收 workspace 权威 runtime、Session 生命周期、Command/ACK、输入账本、封闭 Projection、连接恢复、通用 Agent Profile 和真机 E2E。

Pi

Agent Harness

吸收 AgentMessage/LLM 分层、Steering/Follow-up、Tool 契约、SessionTree、Compaction、Extensions 与 RPC/SDK 共用内核。

Browser Agent

浏览器执行

吸收标签组、CDP guard、页面快照、真实鼠标、文件上传、冻结历史、子 Agent 事件和 Chrome 真机回归。

不照搬 ZCode 的复杂度

ZCode 是数万级模块和完整产品矩阵。本设计只采用其状态协议和可靠性边界，不复制插件市场、Bots、Office、移动远控等全部产品能力。

04

四层状态模型

把实例、任务、对话和 UI 状态混成一个 status 是后续竞态与恢复 bug 的主要来源。

Instance

SessionLifecycle

unloaded、starting、ready、stopping、faulted。回答“实例是否可接收操作”。

Execution

TaskStatus

queued/running/waiting/paused/completed/failed/cancelled。回答“任务执行到哪里”。

Conversation

ConversationPhase

draft/prewarming/running/completed/error。回答“本轮对话是否还需要用户等待”。

UI

Local UI State

草稿、滚动、焦点、面板开合和 optimistic overlay。回答“当前客户端正在如何展示”。

Session 生命周期

unloaded -> starting -> ready
ready -> stopping -> unloaded
starting -> stopping -> unloaded | faulted
stopping -> faulted

Invariant:
ready != idle
stop accepted != resources released

Conversation 完成门槛

running while foregroundWork.length > 0

foregroundWork:
  primary turn
  foreground subagent
  compaction
  goal verification / continuation
  pending permission interaction

backgroundBash / backgroundSubagent:
  session-owned but non-blocking
关闭契约

Session stop/restart 必须停止准入、广播取消、等待所有 owned foreground/background work 和持久化收尾，再释放 MCP、Browser、Sandbox 和 Store 引用。超时不能伪装成已关闭。

06

Control Plane / Connection Gateway

客户端只发送 Command、消费 Projection；连接层只做可信上下文、订阅所有权和受限转发。

M1

Control Plane / Connection Gateway

命令、订阅、投递 profile 和断线恢复

P0 · Critical
ZC-A1ZC-A2ZC-A5UP-A1

设计要点

  • Host 为每个 attachment 注入不可伪造的 connectionId、clientMode、deliveryProfile。
  • Side Panel 使用 continuous；Web/手机远控使用 replayable。
  • 订阅按 connectionId + subscriptionId 精确路由，不广播后丢弃。
  • snapshot 整体替换；delta 必须连续；gap 触发单飞 resync。
  • UI 的 optimistic overlay 只按 commandId 收口，不进入权威 store。
  • 关闭连接只清理该 connection 的订阅和缓冲。

核心对象

interface TrustedConnection {
  connectionId: string;
  clientId: string;
  mode: "desktop-continuous" | "web-replayable";
  delivery: "continuous" | "replayable";
}

interface Subscription {
  subscriptionId: string;
  connectionId: string;
  topic: string;
  logEpoch: string;
  sentSeq: number;
}

交互

客户端发送 hello、subscribe 和 command。Gateway 校验连接身份，向 runtime 注入可信上下文；Projection 帧只发回 subscription owner。断线重建后旧 profile 不继承，重新握手。

行为基线

ZC-A1/A2/A5 适配采用：保留可信 attachment、owned subscription、continuous/replayable 与单飞 resync。实现从单机多客户端起步，不先做复杂 relay。

验收

  • 一个客户端慢消费不阻塞另一个连接。
  • 无 base 时必须 snapshot，不伪造 seq=0。
  • 重复/迟到帧不重复修改投影。
  • 一个 attachment 关闭只释放自己的订阅。
07

Workspace Runtime

每个 workspace 只有一个权威任务入口；同一 workspace 的多个 session 可以并行。

M2

Workspace Runtime

Session 路由、runtime generation 与资源所有者

P0 · Adopt ZCode
ZC-A1ZC-A3TL-A1

设计要点

  • workspaceId 用稳定身份，不用显示路径猜测远程项目。
  • 一个 workspace runtime 持有 SessionRegistry、ProjectionPublisher、ProfileRegistry 和共享资源。
  • 一个 workspace 可以有多个 session；每个 session FIFO 独立。
  • Session A 的 provider 卡住不能阻塞 Session B 的命令。
  • Runtime generation 变化时旧 base 和旧 attachment 全部失效。
  • Browser、MCP、Sandbox 连接按 workspace/session lease 共享，关闭一个 session 不误伤其他使用者。

核心契约

interface WorkspaceRuntime {
  readonly workspaceId: string;
  readonly generation: string;
  ensureSession(sessionId: string): Promise<SessionHandle>;
  routeCommand(command: CommandEnvelope): Promise<CommandAck>;
  subscribe(input: SubscribeRequest): Promise<SubscribeAck>;
  health(): WorkspaceRuntimeHealth;
  shutdown(): Promise<void>;
}

交互

Host 按 workspace 选择或启动 runtime；所有命令与订阅进入 runtime。Runtime 根据 sessionId 路由到对应 CommandInbox 和 ProjectionPublisher，但保留共享 Provider、MCP、Browser、Artifact 和 Store 的资源所有权。

行为基线

ZC-A1 直接采用：每 workspace 单权威 runtime。与桌面产品的差异是首版可放在扩展 offscreen document、独立 worker 或本地服务，接口保持一致。

验收

  • 不同 workspace 不串 session 或文件。
  • 同 workspace 多 session 可并行独立运行。
  • Runtime generation 变化会强制客户端 snapshot。
  • Shutdown 等待所有 session owner 完成收尾，或明确 faulted。
08

SessionLifecycleController

实例生命周期必须独立于任务和聊天状态。

M3

SessionLifecycleController

装载、停止、重启、故障和资源收尾

P0 · Direct borrow
ZC-A3ZC-A1TL-A1

设计要点

  • 状态：unloaded、starting、ready、stopping、faulted。
  • ready 仅表示可接收操作，不等于空闲。
  • getState 绝不隐式激活 session。
  • ensureReady、stop、restart 在第一次 await 前登记操作所有权。
  • stop 先关闭准入，再取消工作，再等待持久化与资源释放。
  • 清理失败或无法确认时进入 faulted，禁止自动新建替代实例。
  • restart 跨越 stopping → unloaded → starting → ready，中途不能抢占。

核心状态

interface SessionLifecycleSnapshot {
  sessionId: string;
  state: "unloaded" | "starting" | "ready"
       | "stopping" | "faulted";
  generation: number;
  revision: number;
  activeOperation?: "ensureReady" | "stop" | "restart";
  lastError?: { operation: string; code: string; message: string };
}

交互

Host 的打开、恢复、自动回收、删除和进程退出都进入同一个 LifecycleController。Projection 是 Lifecycle 的观察者，不是激活者；命令 admission 在 lifecycle ready 后才允许。

行为基线

ZC-A3 直接采用。这是之前设计的明确缺口：TaskRuntime 的 queued/running 不能代替“实例是否 ready”。

验收

  • 查询状态不会创建实例。
  • 并发 ensureReady 只创建一个实例。
  • stop 返回成功表示资源确实完成释放。
  • 清理超时进入 faulted，迟到完成不能解除 faulted。
09

TaskRuntime / CommandInbox / Input Ledger

命令是唯一变更入口，任务图负责执行与所有权，输入账本保证 ACK 后不蒸发。

M4

Command + Task Runtime

幂等、单写者、输入生命周期、预算与恢复

P0 · Critical
ZC-A2ZC-A6TL-A1TL-A2

设计要点

  • conversation mutation 必须带 commandId、clientId、sessionId、baseRevision；row-targeting 命令带 baseLogEpoch。
  • ACK 状态：accepted/rejected/stale/duplicate/noop/failed。
  • 同 session 单写者 FIFO；同 commandId 共享同一个最终结果 Promise。
  • 输入先写 durable ledger，再进入 runtime queue 或 transcript。
  • Ledger 状态：admitted/promoted/cancelled/discarded/failed。
  • 重启后 admitted 输入标为 discarded(session_resumed)，不自动重放。
  • TaskGraph 记录父子任务、等待策略、background 行为和预算。
  • 副作用使用 idempotency key，resume 前查询结果。

核心对象

interface CommandEnvelope {
  commandId: string;
  clientId: string;
  sessionId: string;
  baseRevision?: number;
  baseLogEpoch?: string;
  type: ConversationCommandType;
  payload: unknown;
  issuedAt: number;
}

interface InputLedgerEntry {
  inputId: string;
  sourceCommandId: string;
  status: "admitted" | "promoted"
        | "cancelled" | "discarded" | "failed";
  delivery: "startNow" | "guide" | "queue";
  intent: ConversationInputIntent;
  terminalReason?: string;
}

交互

Gateway 命令进入 CommandInbox，先校验 schema、epoch、revision 和 guard，再写 input ledger。Core admission 原子判断 start/queue/reject；task runtime 维护执行状态。ACK 只表示命令被处理，最终 UI 由 Projection 收口。

行为基线

ZC-A2/ZC-A6 直接采用：Command/ACK、input ledger、stable query、不自动重放。新增 TaskGraph 与 capability 预算，以覆盖沙盒执行。

验收

  • 重复 commandId 不产生第二个任务或副作用。
  • ACK 后崩溃可查询输入的真实终态。
  • stale 命令不静默重放。
  • 父取消递归取消 owned child。
  • 预算耗尽进入 paused，不丢失 task。

AgentSession / AgentLoop

以 Pi 的事件化 Harness 作为模型交互核心，由 TaskRuntime 管理持久生命周期。

M5

AgentSession / AgentLoop

Turn、消息、工具、Steering 与 Follow-up

P0 · Pi baseline
PI-A1PI-A2ZC-A2

设计要点

  • AgentMessage 可包含 UI-only/custom 类型；发送模型前必须 convertToLlm。
  • 事件：agent/turn/message/tool 四级生命周期。
  • steer 在当前工具批次后进入；followUp 在自然停止前进入。
  • prepareRequest、prepareNextTurn、finishTurn 提供扩展点。
  • 工具参数先校验再交给 beforeToolCall。
  • 并行工具完成事件按完成顺序，ToolResult Message 按模型源顺序。
  • 所有 finalized events 进入 TaskRuntime/EventLog，不只存在 Agent 内存。

事件模型

type LoopEvent =
  | { type: "turn_start" }
  | { type: "message_start"; message: AgentMessage }
  | { type: "message_update"; delta: ModelEvent }
  | { type: "message_end"; message: AgentMessage }
  | { type: "tool_execution_start"; callId: string }
  | { type: "tool_execution_update"; callId: string; partial: unknown }
  | { type: "tool_execution_end"; callId: string; result: ToolResult }
  | { type: "turn_end"; message: AgentMessage };

交互

TaskRuntime 调用 AgentSession；AgentSession 构建投影并进入 AgentLoop。ModelGateway 返回统一事件，ToolExecutor 执行工具，SessionTree 持久化消息与工具结果。

行为基线

PI-A1/A2 直接采用。这是内核行为基线，不因引入 ZCode 产品协议而重写。ZCode 的 Command/Projection 包在 Harness 外层。

验收

  • Steering 不跳过当前工具。
  • Follow-up 只在一个 run 的自然停止前进入。
  • 自定义消息未经转换不会发送模型。
  • Abort 贯穿模型、工具、压缩和子任务。
11

SessionTree / Canonical Facts

持久历史采用 Pi 的树模型，产品投影采用 ZCode 的 canonical facts 归一思路。

M6

SessionTree / Canonical Facts

消息、分支、上下文编辑、冷恢复和稳定身份

P0 · Pi + ZCode
PI-A4ZC-A4ZC-A6

设计要点

  • SessionEntry 使用 id/parentId 构树，active leaf 决定上下文。
  • Entry 支持 message、model change、usage、compaction、branch summary、context edit、custom。
  • Live event 和 cold persistence 都归一为 CanonicalFact。
  • 可操作 product row 使用稳定 entityId/productTurnId，不使用展示 rowId。
  • 排序使用 normalizedOrderKey，而非时间戳猜测。
  • 原始历史只读；context edit、compact 和 fork 只影响当前路径投影。
  • SessionLifecycle 重启后未完成 tool/running work 收口为历史终态，不能伪装仍在运行。

核心对象

interface CanonicalFact {
  factId: string;
  entityId: string;
  productTurnId: string;
  orderKey: NormalizedOrderKey;
  source: "persisted" | "live" | "derived";
  kind: FactKind;
  payload: unknown;
}

type NormalizedOrderKey = readonly [
  branchEpoch: string,
  hostMessageSeq: number,
  hostPartSeq: number,
  boundaryRank: number,
  lifecycleOrdinal: number
];

交互

ToolRegistry / ToolExecutor

P0 · Pi + ZCode
PI-A3ZC-A7UP-A2TL-A1

设计要点

  • 工具声明 input/output schema、capability、effect、risk、executionMode、replay 和 timeout。

P0 · Security critical

设计要点

SubagentCoordinator

ZC-A8ZC-A9UP-A3TL-A1TL-A2

设计要点

  • Researcher/Reviewer 仅作为内置 Profile，删除它们不影响内核。
  • 用户/插件可新增任意 Profile。

  • 无工具最终文本不能直接完成；调用 Verifier 检查页面状态、测试、diff 或 artifact。
  • 失败验证产生结构化 observation 并触发 replan。

核心对象

interface PlanState {
  mode: "off" | "planning" | "approved";
  previousMode?: PermissionMode;
  items: Array<{
    id: string;
    title: string;
    status: "pending" | "running" | "done" | "failed";
    acceptance?: string;
  }>;
  approvedPlanArtifactId?: string;
  openQuestions: string[];
}

interface VerificationResult {
  ok: boolean;
  checks: Array<{ name: string; ok: boolean; evidence: ArtifactRef[] }>;
  nextAction?: string;
}

交互

模型调用 EnterPlanMode → 只读探索 → AskUserQuestion 澄清 → ExitPlanMode → 用户审批 → 写批准计划 artifact → 恢复原模式。任务完成前 Verifier 消耗测试/页面/产物证据。

行为基线

ZC-A10 直接采用：Enter/Exit PlanMode、批准计划持久化和 compact 连续性。PI-A2 提供 finishTurn/continuation hook。Verifier 是本设计原创补强。

验收

  • Plan mode 中写工具被策略拒绝。
  • 计划未批准不能进入实现。
  • compact 后仍能恢复批准计划。
  • 无证据完成声明不能进入 completed。

设计要点

Workspace / SandboxProvider

真正的受限 Coding 环境。权限模式和 tool approval 不是沙盒。

M18

Workspace / SandboxProvider

文件、PTY、测试、网络、快照和 SecretBroker

P2 · Differentiator
ZC-A7PI-A3RISK-ZCTL-A3

设计要点

  • 独立容器/microVM；扩展和 Agent 不直接拥有宿主文件/进程权限。
  • 只有 workspace root 可写，根文件系统和宿主敏感目录不可见。
  • 文件、patch、search、git、test、process 都是原子 capability。
  • PTY 有 session、流式输出、超时、背压和真实取消。
  • 网络默认关闭，通过代理做域名 allowlist 和 DNS/IP 检查。
  • SecretBroker 注入短时、作用域凭据；命令与 artifact 不含明文。
  • CPU、内存、PID、磁盘、时间和输出有硬限制。
  • Snapshot/rollback；写型子 Agent 使用独立 worktree。
  • 资源释放由 workspace/session lease 管理，关闭一个 session 不误伤其他租户。

核心契约

interface SandboxProvider extends ExecutionProvider {
  createWorkspace(sessionId: string, template: WorkspaceTemplate): Promise<WorkspaceRef>;
  readFile(path: string): Promise<FileChunk>;
  applyContextPatch(patch: ContextPatch): Promise<PatchResult>;
  applyUnifiedDiff(patch: UnifiedPatch): Promise<PatchResult>;
  search(query: SearchQuery): Promise<SearchResult[]>;
  startProcess(spec: ProcessSpec, signal: AbortSignal): Promise<ProcessHandle>;
  runTests(spec: TestSpec, signal: AbortSignal): Promise<TestReport>;
  snapshot(ref: WorkspaceRef): Promise<SnapshotRef>;
  restore(snapshot: SnapshotRef): Promise<void>;
  releaseWorkspace(ref: WorkspaceRef): Promise<void>;
}

交互

ToolExecutor 将代码动作路由到 SandboxProvider；模型默认使用上下文 Patch DSL，内部生成 unified diff；外部标准补丁使用独立入口。PolicyEngine 校验工作区、网络和命令能力；Verifier 消费 TestReport；ArtifactStore 保存 diff/日志；SessionLifecycle stop 等待进程、PTY、日志和 volume lease 释放。

行为基线

PI Tool 契约和 ZCode 权限/进程管理纪律适配采用。RISK-ZC明确：yolo 不是沙盒。目标是安装主机零信任，由独立执行层实施限制。

验收

  • 路径穿越、symlink 和绝对宿主路径逃逸失败。
  • 网络默认关闭且 allowlist 外请求失败。
  • 资源超限和取消可观测。
  • Session stop 无孤儿进程或 volume lease。
  • 测试、diff、artifact 可作为完成证据。

验收标准

每项都应通过自动化 fixture、契约测试或真机测试证明。

权威状态

  • UI 关闭后 runtime 任务继续。
  • 同 commandId 重复发送只有一个结果。
  • ACK 丢失可通过 commands/query 对账。
  • 重启后 admitted 输入明确 discarded。
  • Runtime 重启强制 snapshot，不复用旧 seq。

生命周期

  • ready 与 idle 分离。
  • query 不激活 session。
  • 并发 ensureReady 只创建一个实例。
  • stop 成功代表全部资源已释放。
  • 清理失败进入 faulted 且不自动重建。

会话与上下文

  • live/cold projection golden 一致。
  • delta gap 恢复不产生半应用状态。
  • tool call/result 不被压缩拆开。
  • Plan/Marker 位置由 stable anchor 决定。
  • 原始历史、fork 和 context edit 可追溯。

通用子 Agent

  • 新增 Profile 不需要修改 Coordinator。
  • 子 Agent 权限不能超过父任务。
  • foreground/background 完成门槛正确。
  • 父取消清理全部 owned child。
  • 写型 child 只在 worktree/sandbox 中执行。

权限与扩展

  • Plan mode 在策略层阻止写操作。
  • 项目 Hook 摘要变化后授权失效。
  • 扩展不能注册超 manifest 权限。
  • Skill 正文按需加载。
  • sandbox-auto 不适用于宿主动作。

沙盒

  • 路径、symlink 和宿主挂载逃逸失败。
  • 网络默认关闭，私网和 DNS rebinding 受限。
  • CPU/PID/内存/磁盘/时间可限制。
  • 停止 session 无孤儿进程或租约。
  • 测试、diff、artifact 可作为完成证据。
开发前需要评审确认的决策
  • WorkspaceRuntime 首版放扩展 offscreen document、后台 worker，还是独立本地服务？
  • 是否直接依赖 Pi Agent Core，还是做接口兼容的本地实现？
  • Side Panel 与 Web 是否首版都需要，还是先做单客户端？
  • ProductProjection 是否需要像 ZCode 一样完整 rows window，还是先较小 schema？
  • Agent Profile 的来源和同名覆盖规则是否采用“用户覆盖项目”？
  • 默认并发的 background 子 Agent 是 1 还是 2？
  • Sandbox 优先容器、microVM，还是远程 Linux 主机？
