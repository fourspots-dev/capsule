讨论决定的捕获、分类与 ADR 主动发起

把讨论中出现的长期决定先记录为 DEC-NNN，再由 Agent 在明确检查点进行分类；满足架构条件时主动生成 Proposed ADR 并请求用户确认。ADR 不再必须依附于一个已经存在的 REQ。

1. 目标与非目标

目标

  • 讨论中的长期决定无需先有 REQ 即可留痕。
  • Agent 在固定检查点自动进行 ADR triage，不依赖用户提醒。
  • 需要新 ADR 时自动生成 Proposed ADR、关联来源并请求确认。
  • 未解决或待确认的架构决定阻止详细设计进入 Approved 和实现进入 In Progress。
  • DEC、ADR、REQ 之间可双向追溯。

非目标

  • 不把每句用户意见都永久保存为 DEC。
  • 不自动接受 Agent 起草的 ADR。
  • 不把全文聊天记录复制进仓库。
  • 本阶段不实现 TUI/浏览器的可视化决策卡片，但定义统一事件语义。
  • 不以关键词规则替代 Agent 对语义和架构影响的判断。
核心分工：Agent 负责识别、记录、分类和起草；registry/checker 负责阻断遗漏和错误关联；用户只裁决真正需要架构选择的内容。

3. 核心对象与类关系

DecisionRegistry
  └─ DecisionRecord (DEC-NNN)
       ├─ source / statement / normalizedDecision
       ├─ scope[]
       ├─ triage
       │    ├─ disposition
       │    ├─ requirements[]
       │    └─ adrs[]
       └─ status / supersededBy

AdrRegistry
  └─ ArchitectureDecision (ADR-NNN)
       ├─ originDecision? -> DEC-NNN
       ├─ requirements[]   (可为空)
       ├─ supersedes / supersededBy
       └─ status

RequirementRegistry
  └─ Requirement (REQ-AREA-NNN)
       └─ adrReview
            ├─ status: pending|existing|proposed|not_required
            ├─ adrs[]
            ├─ rationale
            └─ reviewedAt

Checkers
  ├─ DecisionRegistryChecker
  ├─ AdrRegistryChecker
  └─ RequirementTraceabilityChecker
对象所有者生命周期
DecisionRecordAgent 捕获，用户可纠正captured → triaged/promoted/no_action/withdrawn；编号永久

ADR provenance

Requirements: REQ-NNN | none
Origin decision: DEC-NNN | none
  • 每个 ADR 必须至少有一个来源：受影响 REQ 或 DEC。
  • `existing` 只能引用 Accepted ADR；`proposed` 只能引用 Proposed ADR。
  • `not_required` 必须有不以“无架构影响”概括的空泛理由。
  • `pending` 不能进入设计 Approved 或实现 In Progress。
  • DEC 编号和 ADR 编号都永不复用。
  • DEC 来源不能被 ADR/REQ 替代后删除。

6. 端到端交互

1 · Sweep识别长期决定
2 · Capture写 DEC
3 · TriageREQ/ADR/局部/忽略
4 · Propose需要时建 ADR
5 · Confirm用户裁决
6 · Gate设计批准与实现授权

Agent 自动发起语义

decision_required
  decision_id: ADR-013
  origin_decision: DEC-001
  title: Agent-initiated decision intake and ADR triage
  summary: ...
  alternatives: [...]
  affected_surfaces: [...]
  linked_requirements: [...]
  choices: [accept, reject, revise]

CLI 可以在回合结束时展示该评审包；TUI/浏览器未来渲染为卡片，但都消费同一对象。用户未作出选择前，Agent 不得继续依赖该决定的实现工作。

减少打扰

  • 没有长期影响的讨论不创建 DEC。
  • 多个 DEC 在自然阶段收口时合并为一个评审包，但每个 ADR 仍是一项决定。
  • 新 ADR 可与 REQ 详细设计一起评审，但 ADR 接受、设计批准、实现授权三个状态独立。

7. 失败、恢复与安全边界

错误行为恢复
DEC duplicate id校验失败分配下一个未使用编号，不修改旧记录
Promoted DEC 引用未知 ADR/REQ校验失败补齐实体或降级为 triaged/no_action
ADR 无 REQ 且无 DEC校验失败记录 Origin decision，或关联实际 REQ
adrReview pending阻断设计 approved 和实现完成 triage 并记录理由
Proposed ADR 被当作当前约束requirements 校验失败等待用户确认后才进入 existing
DEC 文件被删除孤立/缺失校验失败从 Git 恢复；编号不可复用
仓库只保存决定及最小来源，不保存完整对话、Secret 或无关个人信息。DEC 不是运行时日志，也不进入 Workspace Capsule。

8. 兼容与迁移

  • 0.5.0 之前已完成的 REQ 不回填 adrReview。
  • targetVersion ≥ 0.5.0 的未完成 REQ 必须补 adrReview，并引用现有 ADR 或记录 not_required 理由。
  • 现有 ADR 增加 Origin decision: none，不改变其含义。
  • ADR-013 是新来源模型的首个实例：DEC-001 → ADR-013 → REQ-ENG-006。
  • registry schema 保持 version 1，通过新增可选/受版本约束字段向后兼容。

9. 验收条件

  • Agent 在没有用户要求时会执行 decision sweep，并在讨论形成长期决定后创建 DEC。
  • Agent 在 REQ 设计前完成 adrReview，满足条件时主动生成 Proposed ADR。
  • 无 REQ 的 ADR 仅在存在 Origin decision 时合法。
  • Proposed ADR 或 pending review 无法通过实现门禁。
  • DEC、ADR、REQ 正文与 registry 双向一致。
  • `npm run decisions:check` 已进入 `npm run check`。
  • 详细测试设计中的正常、负向、边界和端到端案例全部通过。
