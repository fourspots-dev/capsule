UI TEST STRATEGY · v1.0

每条过程展示都必须有确定性证据

测试重点不是截图是否“看起来差不多”，而是证明 Projection 到 UI view model 的派生正确、运行态与终态行为稳定、工具和审批不丢信息、恢复不制造第二份状态。

对应设计 tinyai UI Design v1.0 现有基线 159 deterministic / 3 Chrome E2E 视觉基线 initial tinyai 420×900 状态 待评审
测试先行边界

UI 只从 Projection 和 Runtime 命令构造。测试必须使用 fake/replay 数据覆盖所有状态，真实模型仅用于少量非阻塞 Live Eval。

02

测试策略

L0 Contract

纯函数派生、schema、状态机不依赖 DOM。

L1 Unit

Renderer registry、折叠、滚动和 Composer 逻辑。

L2 Integration

KernelClient、Gateway、Projection 和 Chrome API fake。

L3 E2E

真实 Chrome、真实 Side Panel、受控本地模型服务。

Live Model Eval 属于 L4，只评估模型行为与质量，不替代确定性门禁。任何 UI 状态机问题必须能在 L0–L3 复现。

06

思考展示

Provider 有 reasoning

  • 首块始终有入口
  • 默认收起
  • 流式更新不自动展开
  • 完成后保留内容

Provider 无 reasoning

  • 只显示真实运行状态
  • 不能生成伪 reasoning 文本
  • “Thinking”不得被标记为模型思考内容

用例至少包含 DeepSeek Reasoner 的 reasoning_content、普通模型无 reasoning、reasoning 中断和设置开关四种输入。

08

通用子 Agent

  • 任意 Profile 名、图标/颜色、模型、tools、permissions 均来自 profile；UI 无角色白名单。
  • 父会话只显示摘要，不镜像 child rows。
  • View 打开 child session；返回恢复父会话与滚动位置。
  • foreground/background、stop、send message、completion 都更新摘要。
  • child 失败不能导致父消息误标成功；父取消会清理 child。
  • 缺少 color 时使用稳定 hash fallback，不表达错误语义。
09

Composer 与队列

输入

  • Enter 发送，Shift+Enter 换行
  • IME 合成不发送
  • 草稿按 session scope 隔离
  • 附件/技能/标签页引用恢复

压缩

  • 320px 无横向溢出
  • 模型/审批按优先级收为图标
  • 发送和输入始终可见

队列

  • queue 只来自 Projection
  • 删除/排序/立即发送以 ACK 为准
  • 撤回编辑跨会话不得串写
10

审批、问答与接管

  • 点击与填表审批按 Browser Action family 显示目标和风险。
  • 文件/终端/脚本审批必须显示实际对象和副作用。
  • 等待审批或用户输入时隐藏 ChatLoading，不误报“正在思考”。
  • 重复审批响应必须幂等；过期/陈旧响应有明确提示。
  • Handoff Continue 后先重新观察页面，再继续任务。
  • Settings 打开期间底层审批不能抢焦点。

响应式、主题与无障碍

320px

无横向滚动；控件不重叠；次要标签隐藏。

390px

主目标宽度；Composer 无换行错位。

736px

状态和侧栏展开不挤坏正文。

1024px

侧面板与内容宽度稳定。

无障碍检查清单
  • Tab 顺序遵循视觉顺序
  • 折叠入口有 aria-expanded
  • 图标按钮有 aria-label
  • 动态计时低频 aria-live
  • Settings 打开时底层 inert
  • 减少动态效果下无持续 shimmer
  • 文本与语义背景对比度 ≥ 4.5:1

状态空间与 Property Test

stateDiagram-v2
  [*] --> Draft
  Draft --> Running: accepted

  • 随机生成 row 顺序、delta 重复、乱序和断线点，验证最终投影唯一。
  • 随机生成工作段和折叠操作，验证任何终态都不会丢失最终回答。
  • 随机合并合法工具 family，验证聚合不改变原 row identity 和顺序。
  • 随机调整 Composer 宽度，验证关键控件始终可达且无横向溢出。
15

性能与虚拟化

  • 5000 轮、50000 rows 重放，渲染首帧不应遍历全部不可见内容。
  • 虚拟滚动单位是 TurnRenderUnit，用户输入与对应回答不得分离。
  • 流式 delta 只更新当前 work segment 和必要索引。
  • 用户离开底部后，布局增长不得抢回 scrollTop。
  • 计时只更新文本，不重算 TurnRenderUnit 或历史工具。
  • 无 reduced-motion 才启用 shimmer；动画不得阻塞输入。
16

Fixture 规范

{
  "fixtureVersion": 1,
  "name": "running-to-completed-history",
  "projection": {
    "phase": "completed",
    "taskStatus": "completed",
    "rows": []
  },
  "events": [],
  "expected": {
    "turnCount": 1,
    "historyOpen": false,
    "latestAssistantVisible": true,
    "toolFamilies": ["Explore"]
  }
}
  • Fixture 禁止真实 API Key、浏览器 Cookie 和用户页面正文。
  • 每个 fixture 固定 UUID、时间、model output 和工具结果。
  • 截图测试必须同时有 semantic snapshot，避免“像素正确但状态错误”。
  • 失败时输出 DOM snapshot、projection、event seq、screenshot 和 console。

19

发布门禁

必须通过

  • TypeScript / unit / integration 全绿
  • UI view-model golden 全绿
  • Chrome E2E 001–010 全绿
  • 320/390 无横向溢出
  • 单 UI 入口与 no-legacy 扫描
  • 无未处理 Promise rejection
  • 无 API Key 泄露

视觉与性能门禁

  • 420×900 主界面对照初始截图
  • 折叠入口、发送按钮、消息左右一致
  • 历史过程不进入首帧全量 DOM
  • 流式更新保持输入可交互
  • 用户离底后不被自动拉回
  • 重新打开扩展恢复任务和草稿
不允许用 Live Eval 替代确定性测试

模型回复措辞不稳定。功能正确性必须由 fake/replay 和真实 Chrome fixture 证明；Live 只用于质量、工具选择、压缩连续性和成本评估。
